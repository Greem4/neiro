# Как помочь проекту

Спасибо, что заглянули. Ниже — всё, что нужно, чтобы собрать проект и
предложить правку, а заодно честный ответ на вопрос, почему правку могут не
взять.

## Что это за проект

Neiro — личный инструмент одного педагога, а не продукт. Он решает конкретные
задачи конкретного человека: расписание из YClients, деньги за занятия,
уведомления об изменениях. Исходники открыты, разбор устройства лежит в
[`docs/`](docs/), но приоритет у задач владельца.

Отсюда простое следствие: сообщения о проблемах и предложения приветствуются,
но крупную правку лучше сначала обсудить в issue. Готовый PR, который меняет
поведение под чужой сценарий, скорее всего не будет принят — не потому что он
плохой, а потому что приложение остаётся личным.

## Как собрать

Порядок — в README, раздел [«Быстрый старт (разработка)»](README.md#быстрый-старт-разработка).
Коротко и честно про то, чего у вас не будет:

- **без `local.properties`** проект соберётся, но вход не пройдёт: приложение
  не знает адреса и ключа сервиса Neiro, а данные YClients идут только через
  него;
- **без `app/google-services.json`** проект соберётся тоже — с выключенным
  FCM, то есть без push. Календарь, архив и синхронизация при этом работают.

То есть собрать и запустить получится у любого, увидеть боевые данные — нет.
Для разбора кода этого достаточно.

## Правила коммитов

Одна строка, до 72 символов, по-русски, глагол в прошедшем времени. Без тела
коммита, без префиксов `feat:` / `fix:`, без перечисления файлов и классов —
одна главная мысль. Имена в коде можно латиницей, описание — только русский.
Те же правила действуют для агентов, они записаны в [CLAUDE.md](CLAUDE.md).

Так:

- `Добавил API ежемесячных выплат Pay`
- `Исправил жесты drawer с левого края`
- `Обновил PayMonthlyChart`

Не так:

- `Добавлены новые модели и маршруты… Обновлены стили…` — несколько мыслей
- `Refactor CalendarHeader for improved usability` — английский и префикс
- `Правки` — не сказано, что изменилось

## Ветки и PR

Ветка отводится от `main`. Один PR — одна мысль: пять несвязанных правок
в одной ветке невозможно ни разобрать, ни откатить по частям. Описание
подставится из [шаблона](.github/pull_request_template.md) — заполните, что
меняется и как вы это проверили.

Пуш тега и выпуск релиза делает владелец, порядок описан в
[docs/updater/RELEASE.md](docs/updater/RELEASE.md).

## Тесты

Перед отправкой:

```bash
./gradlew :app:testDebugUnitTest
```

Тесты должны быть зелёными. Если правка меняет поведение, покрытое тестом, —
тест правится тем же PR, а не «потом отдельно».

## Что обсуждается до кода

Эти вещи лучше сначала вынести в issue, иначе есть риск написать код, который
не примут:

- **новые зависимости** — каждая библиотека остаётся в проекте надолго и
  тянет обновления;
- **правки [`docs/updater/ARCHITECTURE.md`](docs/updater/ARCHITECTURE.md)** —
  документ описывает принятые решения, менять его на ходу нельзя;
- **всё, что трогает push-контур** (`neiro-push/`, `app/.../push/`) и
  **синхронизацию YClients** — там живут чужие данные и токены, поломка
  видна не в тестах, а на телефоне у человека;
- **расчёт денег** — цифры сверяются с реальными выплатами, «улучшение»
  формулы без разговора обычно означает расхождение с фактом.
