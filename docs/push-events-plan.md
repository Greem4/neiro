## 0. Инструкция исполнителю

Раздел для агента, который будет реализовывать план.

### Работать этапами, коммитить каждый

Один этап = одна законченная порция = один коммит. **Не начинать следующий
этап, не закоммитив предыдущий. Не сваливать несколько этапов в один коммит** —
именно так появился коммит `51d8fe3` на ~40 правок, в котором незамеченным
проехал баг, убивший уведомления.

Порядок работы над этапом:

1. Прочитать раздел этапа целиком.
2. Сделать.
3. Прогнать проверку из «Приёмки» этапа.
4. Закоммитить.
5. Коротко доложить пользователю: что сделано, что проверено.

### Формат коммитов

По правилам репозитория ([CLAUDE.md](../CLAUDE.md)): одна строка на русском,
до 72 символов, глагол в прошедшем времени, без префиксов `feat:`/`fix:`,
без перечисления файлов и деталей реализации.

| Этап | Сообщение коммита |
|---|---|
| 1 | `Добавил каркас сервиса событий neiro-push-events` |
| 2 | `Добавил схему базы сервиса событий` |
| 3 | `Добавил запрос записей YClients на всю компанию` |
| 4 | `Добавил вычисление событий по изменениям записей` |
| 5 | `Добавил опрос YClients и отправку событий в push` |
| 6 | `Добавил API регистрации и догона событий` |
| 7 | `Добавил дашборд сервиса событий` |
| 8.1 | `Убрал локальный опрос YClients из приложения` |
| 8.2 | `Добавил показ уведомлений из payload push` |
| 8.3 | `Добавил догон пропущенных событий с сервера` |
| 9 | `Добавил документацию сервиса событий` |

## 1. Задача и рамки

Получать уведомление на телефон о **каждом конкретном изменении занятия**:
ребёнок подтвердился, отменился, пришёл, запись перенесли, добавили, удалили.
Это ключевая функция приложения — пропущенное уведомление считается аварией.

### Жёсткие рамки

| Рамка | Смысл |
|---|---|
| **Версия 0.6.9.0 работает — не трогаем** | Существующий сервис `neiro-push` и текущая сборка приложения остаются как есть. Никаких правок в `server/` |
| **Новый сервис ставится рядом** | Отдельный контейнер, отдельная база, отдельный порт. Старый и новый работают одновременно и не мешают друг другу |
| **Опрос раз в 10 с** | Вместо нынешних 15 с |
| **Сервер — единственный, кто опрашивает YClients** | Локальный опрос с телефона в новой сборке приложения убирается, обратно не возвращается |
| **Прозрачность** | Должна быть возможность зайти и увидеть, что происходит |

### Что уже проверено

- **Права токена достаточны**: видно всех специалистов центра, глубина
  просмотра большая. Значит можно делать **один запрос на компанию** вместо
  запроса на каждого специалиста (см. §9.1).

## 2. Как работает существующий сервис

```
YClients ──(опрос 15 c)──> neiro-push ──FCM {action:"sync"}──> телефон
                                                                  │
                                             телефон сам идёт в YClients,
                                             перечитывает МЕСЯЦ целиком,
                                             сравнивает свой снимок до/после
                                             и только тогда понимает, что
                                             «Ваня подтвердился»
```

**Сервер** ([server/app/poller.py](../server/app/poller.py)):
- `fetch_records(changed_after=...)` забирает изменившиеся записи со всеми
  полями: `attendance`, `deleted`, `client_name`, `date`, `datetime`;
- [`yclients.py:fingerprint()`](../server/app/yclients.py) схлопывает весь набор
  в один SHA-256 и сравнивает с сохранённым;
- при расхождении шлёт FCM `{action: "sync", company_id, staff_id, reason}` —
  **без информации о том, что изменилось**.

**Приложение**: `NeiroFirebaseMessagingService` → `PushSyncWorker` →
`refreshLiveRange()` → перечитывание месяца → диф `dayData` до/после →
`SessionChangeDetector` → показ уведомления.

## 3. Проблемы существующей схемы

### П1. Сервер знает ответ, но выбрасывает его
Записи с `attendance` уже на руках, но сводятся к одному хешу. Телефон делает
ту же работу заново и дороже.

### П2. Потерянный push = потерянное событие навсегда
Сервер после отправки двигает `records_fingerprint` и считает, что доставил.
Если FCM не долетел (Doze, OEM-убийца батареи, нет сети) — повтора не будет
никогда. **Механизма догона не существует.** Главный риск.

### П3. Ложные пуши
`fingerprint` считается по набору, отфильтрованному скользящим `changed_after`.
Окно уезжает вперёд → набор меняется сам по себе → хеш другой → push вхолостую.
Каждый такой push стоит телефону перечитывания месяца.

### П4. Каждый push дорогой
`mergeIncrementalRecords` → `getRecords(месяц)` — многостраничный запрос
к YClients с телефона, на батарее, ради вывода, который сервер уже сделал.

### П5. Запрос на каждого специалиста
`accounts` имеет `UNIQUE(company_id, staff_id)` — каждый спец отдельный аккаунт
со своим запросом. Шесть спецов одного центра = шесть запросов каждые 15 с по
одному и тому же календарю.

### П6. Вечером опрос раз в час
`quiet_start_hour = 21`, ночной интервал 3600 с. Подтверждения на завтра идут
как раз вечером.

## 4. Решения и почему

| Решение | Почему |
|---|---|
| Сервер вычисляет типизированные события и кладёт их в payload push'а | Убирает П1 и П4: телефон показывает уведомление, не ходя в YClients |
| Журнал событий + догон по курсору | Убирает П2: потерянный push подхватывается при открытии приложения или на keepalive-тике |
| Состояние по `record_id` вместо общего хеша | Убирает П3, плюс перенос занятия определяется однозначно |
| Один запрос на компанию, разбор по `staff_id` в памяти | Убирает П5. Прав токена хватает — проверено |
| Дневной режим до 23:00 | Убирает П6. Ночной интервал остаётся часовым: после 23 в YClients никто не работает |
| **`dedupeKey` считает приложение, не сервер** | `normalizeForKey()` ([UpcomingSession.kt:185](../app/src/main/java/ru/greemlab/neiro/notifications/UpcomingSession.kt#L185)) нетривиален: сортировка токенов, `ё`→`е`, чистка пунктуации. Повтор на Python = риск расхождения = дубли уведомлений |
| Календарь обновляется только при открытии приложения | Push становится почти бесплатным. Уведомление уже сказало, что случилось; к моменту, когда пользователь откроет календарь, `LiveApiCoordinator.onStart` его освежит |
| Новый сервис рядом, а не переделка старого | 0.6.9.0 работает. Откат = остановить контейнер |

## 5. Целевая архитектура

```
                      ┌─ neiro-push (старый, порт 8010) ──> 0.6.9.0 ──> работает как работал
YClients ─────────────┤
                      └─ neiro-push-events (новый, порт 8011)
                                   │
                     1 запрос на компанию раз в 10 с
                                   │
                     дифф по record_id → события
                                   │
                    ┌──────────────┴──────────────┐
                    │                             │
           журнал events (БД)            FCM с payload события
                    │                             │
                    │                             ▼
                    │                  новая сборка приложения
                    │                  показывает уведомление сразу,
                    │                  БЕЗ похода в YClients
                    │
           GET /v1/devices/{id}/events?since=<курсор>
                    │
                    ▼
          догон при открытии приложения
          и на keepalive-тике
```

### 5.1 Как два сервиса уживаются

| Что | Старый | Новый |
|---|---|---|
| Каталог в репозитории | `server/` (заморожен) | `neiro-push-events/` |
| Контейнер | `neiro-push` | `neiro-push-events` |
| Порт | `127.0.0.1:8010` | `127.0.0.1:8011` |
| База | `/data/neiro_push.db` | `/data/neiro_push_events.db` (свой том) |
| Публичный путь | `https://push.neiro.greemlab.ru/` | `https://push.neiro.greemlab.ru/v2/` |
| Кто ходит | сборка 0.6.9.0 | новая сборка приложения |

**Разделение по сборкам приложения.** `NEIRO_PUSH_API_BASE_URL` — поле
`buildConfigField` ([app/build.gradle.kts:66](../app/build.gradle.kts#L66)),
задаётся в `local.properties`. Старая сборка смотрит на старый URL, новая — на
`/v2`. Устройство регистрируется ровно на одном сервисе, поэтому **двойных
уведомлений быть не может**.

**Маршрут в Caddy — по пути, не по поддомену.** Новый поддомен потребовал бы
DNS и сертификат; путь `/v2/*` на существующем хосте ничего этого не требует.

**Нагрузка на YClients в период сосуществования.** Старый сервис опрашивает раз
в 15 с (запрос на спеца), новый — раз в 10 с (один запрос на компанию). Это
нормально, но после переезда старый сервис надо погасить, а не оставлять
навсегда.

### 5.2 Три независимых пути доставки

| Путь | Когда срабатывает | Стоимость |
|---|---|---|
| Payload в push | Обычный случай, мгновенно | ~0 |
| Догон по курсору | Push потерялся | Крошечный запрос к своей малине |
| Локальный diff при синке | Сервер лёг / FCM выключен | Обычный синк при открытии |

Дубли невозможны: их гасит существующий `wasEventNotified(dedupeKey)` — LRU на
300 ключей в
[SessionNotificationPreferences.kt:117](../app/src/main/java/ru/greemlab/neiro/notifications/SessionNotificationPreferences.kt#L117).
Кто первый принёс событие, тот и показал.

## 6. Контракт

### 6.1 FCM data-payload

Все значения FCM обязаны быть строками.

```jsonc
{
  "action": "session_events",
  "events": "[{\"id\":1234,\"type\":\"CLIENT_CONFIRMED\",\"client_name\":\"Иванов Ваня\",\"date\":\"2026-07-26\",\"time\":\"15:00\",\"kind\":\"LESSON\"}]",
  "last_event_id": "1234"
}
```

| Поле события | Тип | Примечание |
|---|---|---|
| `id` | int | id из журнала, он же курсор |
| `type` | string | `NEW_BOOKING`, `CANCELLED`, `RESCHEDULED`, `DELETED`, `CLIENT_CONFIRMED`, `CLIENT_ARRIVED` — совпадают с `SessionEventType` |
| `client_name` | string | как в YClients, без нормализации. Порядок полей — как в `extractClientName`: `display_name`, иначе `name + surname` ([push-events-app.md §2.2](push-events-app.md)) |
| `date` | string | `YYYY-MM-DD` |
| `time` | string | `HH:MM`, начало занятия. Локальное время подстрокой из `datetime`, **без пересчёта часового пояса** ([§2.1](push-events-app.md)) |
| `kind` | string | `LESSON` \| `DIAGNOSTICS` |
| `prev_date`, `prev_time` | string? | только для `RESCHEDULED` |

**Приоритет.** Data-only сообщение уходит с `android.priority = "high"`, иначе в
Doze доставка откладывается и смысл payload'а теряется.

**Переполнение.** Если сериализованный `events` превышает 3 КБ (лимит FCM ~4 КБ
на сообщение), сервер шлёт нудж `{"action": "sync_events", "last_event_id": "…"}`
— приложение забирает всё через догон.

### 6.2 API нового сервиса

Всё под префиксом `/v2` снаружи (внутри контейнера — обычные пути).

| Метод | Путь | Auth | Назначение |
|---|---|---|---|
| POST | `/v1/devices/register` | API key | Регистрация телефона (как в старом) |
| DELETE | `/v1/devices/{device_id}` | API key | Снятие регистрации |
| GET | `/v1/devices/{device_id}/events?since=&limit=` | API key | **Догон событий** |
| POST | `/v1/devices/{device_id}/events/ack` | API key | Курсор доставки (необязательно, для дашборда) |
| GET | `/health` | Admin key | Статус |
| GET | `/v1/admin/events?limit=` | Admin key | Последние события + доставка |
| GET | `/v1/admin/poll-log?limit=` | Admin key | Последние циклы опроса |
| GET | `/v1/admin/dashboard.txt` | Admin key | **Дашборд простым текстом — для терминала** |
| GET | `/dashboard` | Cookie | Дашборд в браузере (§8.4) |

`/v1/admin/dashboard.txt` и `/dashboard` показывают **одни и те же данные**, но
в двух видах: первый — plain text для `curl` из терминала, второй — HTML для
телефона. Собирать их из одной функции, чтобы не разъезжались.

Ответ догона:

```jsonc
{ "events": [ /* поля из §6.1 */ ], "last_event_id": 1240, "has_more": false }
```

`device_id` отображается на аккаунт через таблицу `devices` — отдельная
авторизация не нужна.

### 6.3 Правила диффа

Коды `attendance` в YClients: `-1` не пришёл, `0` ожидание, `1` пришёл,
`2` подтвердил (см. `AttendanceStatus.fromYClients`).

| Условие | Событие |
|---|---|
| `record_id` раньше не встречался, `deleted = 0`, `attendance != -1` | `NEW_BOOKING` |
| Запись была, стало `deleted = 1` | `DELETED` |
| Было `attendance != -1`, стало `-1` | `CANCELLED` |
| Изменились `date` или `time` | `RESCHEDULED` (+ `prev_date`, `prev_time`) |
| Стало `attendance = 2` | `CLIENT_CONFIRMED` |
| Стало `attendance = 1` | `CLIENT_ARRIVED` |

Если за один опрос изменились и дата/время, и статус — шлём **оба** события:
это два разных факта, ключи у них разные, дублем не будет.

`kind = DIAGNOSTICS`, если какая-либо из `services` содержит «диагностика» без
учёта регистра — та же проверка, что в приложении
([YClientsCalendarSync.kt:722](../app/src/main/java/ru/greemlab/neiro/sync/YClientsCalendarSync.kt#L722)).

### Этап 1. Каркас нового сервиса

Новый каталог `neiro-push-events/` по образцу `server/`, но самостоятельный
(ничего не импортирует из старого):

```
neiro-push-events/
  app/{__init__,main,config,database,security,yclients,events,poller,fcm,dashboard}.py
  templates/dashboard.html
  tests/
  Dockerfile
  docker-compose.yml
  requirements.txt
  .gitignore          # secrets/ .env data/ backups/ __pycache__/
  README.md
```

- Порт `127.0.0.1:8011`, контейнер `neiro-push-events`, том `neiro_push_events_data`.
- `.env`: свои `API_KEY`, `ADMIN_API_KEY`, `TOKEN_ENCRYPTION_KEY`,
  `POLL_INTERVAL_SECONDS=10`, `POLL_NIGHT_INTERVAL_SECONDS=3600`,
  `QUIET_START_HOUR=23`, `DATABASE_PATH=/data/neiro_push_events.db`.
- Секрет FCM: тот же `fcm-service-account.json`, свой каталог `secrets/`.
- **Ротация логов обязательна** — иначе json-файл Docker съест SD-карту:

```yaml
logging:
  driver: json-file
  options: { max-size: "10m", max-file: "5" }
```

- `requirements.txt` — как у старого сервиса плюс `jinja2` (для дашборда).
- Контейнер обязан быть в сети `server_web`, иначе Caddy не достучится по имени.
- Скрипты: `deploy.sh`, `backup.sh`, `restore.sh`, `logs.sh`, `dash.sh` — по
  образцу `server/scripts/` с заменой имён контейнера, каталога и тома.

**Caddy — маршрут по пути внутри существующего vhost.** Сейчас в
`~/server/caddy/Caddyfile` лежит блок вида:

```
http://push.neiro.greemlab.ru {
	reverse_proxy neiro-push:8010
}
```

Новый скрипт `neiro-push-events/scripts/patch-pi-caddy-v2.py` должен вставить
`handle_path` **внутрь** этого блока, перед общим `reverse_proxy`:

```
http://push.neiro.greemlab.ru {
	handle_path /v2/* {
		reverse_proxy neiro-push-events:8011
	}
	reverse_proxy neiro-push:8010
}
```

`handle_path` снимает префикс, поэтому `/v2/health` приходит в сервис как
`/health` — внутри приложения о префиксе знать не надо.

Два требования к скрипту:

1. **Идемпотентность** — повторный запуск ничего не дублирует.
2. **Не ломать старый блок.** Проверено: старый
   [patch-pi-caddy.py](../server/scripts/patch-pi-caddy.py) при повторном
   запуске видит свой маркер `http://push.neiro.greemlab.ru {`, печатает
   `already_patched` и файл не трогает — значит наш `handle_path` он не сотрёт.
   Это поведение важно сохранить: если старый скрипт когда-нибудь поменяют на
   безусловную перезапись, маршрут `/v2` будет затираться при каждом деплое
   старого сервиса.

**Приёмка:** `curl https://push.neiro.greemlab.ru/v2/health` отвечает, старый
`https://push.neiro.greemlab.ru/health` продолжает работать.

### Этап 2. Схема БД

База новая и пустая — миграций и совместимости не требуется, можно сразу
правильно.

```sql
CREATE TABLE accounts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    company_id INTEGER NOT NULL,
    staff_id INTEGER NOT NULL,
    partner_token_enc TEXT NOT NULL,
    user_token_enc TEXT NOT NULL,
    changed_after TEXT,
    backoff_until TEXT,
    consecutive_errors INTEGER NOT NULL DEFAULT 0,
    last_polled_at TEXT,
    last_error TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    UNIQUE(company_id, staff_id)
);

CREATE TABLE devices (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    account_id INTEGER NOT NULL,
    device_id TEXT NOT NULL UNIQUE,
    fcm_token TEXT NOT NULL,
    label TEXT,
    app_version TEXT,
    last_ack_event_id INTEGER,
    last_seen_at TEXT NOT NULL,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    FOREIGN KEY(account_id) REFERENCES accounts(id) ON DELETE CASCADE
);

CREATE TABLE record_states (
    account_id INTEGER NOT NULL,
    record_id INTEGER NOT NULL,
    date TEXT NOT NULL,
    time TEXT NOT NULL,
    attendance INTEGER NOT NULL,
    deleted INTEGER NOT NULL,
    client_name TEXT NOT NULL,
    kind TEXT NOT NULL,
    updated_at TEXT NOT NULL,
    PRIMARY KEY (account_id, record_id),
    FOREIGN KEY(account_id) REFERENCES accounts(id) ON DELETE CASCADE
);

CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    account_id INTEGER NOT NULL,
    type TEXT NOT NULL,
    client_name TEXT NOT NULL,
    date TEXT NOT NULL,
    time TEXT NOT NULL,
    kind TEXT NOT NULL,
    prev_date TEXT,
    prev_time TEXT,
    record_id INTEGER,
    created_at TEXT NOT NULL,
    FOREIGN KEY(account_id) REFERENCES accounts(id) ON DELETE CASCADE
);
CREATE INDEX idx_events_account ON events(account_id, id);

CREATE TABLE push_deliveries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    event_id INTEGER NOT NULL,
    device_id TEXT NOT NULL,
    status TEXT NOT NULL,          -- sent | failed | token_invalid
    detail TEXT,
    created_at TEXT NOT NULL
);
CREATE INDEX idx_deliveries_event ON push_deliveries(event_id);

CREATE TABLE poll_runs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    company_id INTEGER NOT NULL,
    started_at TEXT NOT NULL,
    duration_ms INTEGER NOT NULL,
    records_fetched INTEGER NOT NULL,
    events_created INTEGER NOT NULL,
    pushes_sent INTEGER NOT NULL,
    error TEXT
);
CREATE INDEX idx_poll_runs_started ON poll_runs(started_at);
```

Сразу в `Database.__init__`:

```python
conn.execute("PRAGMA journal_mode=WAL")      # персистентно, один раз на файл
conn.execute("PRAGMA busy_timeout=5000")     # на каждое соединение
conn.execute("PRAGMA synchronous=NORMAL")
```

Один экземпляр `Database` на процесс (в `lifespan`), `_init_schema()` только
на старте — не пересоздавать на каждый HTTP-запрос, как в старом сервисе.

**Приёмка:** контейнер поднимается, схема создаётся, WAL включён
(`PRAGMA journal_mode` возвращает `wal`).

### Этап 3. Клиент YClients — один запрос на компанию

### Этап 5. Поллер и отправка

Файлы `app/poller.py`, `app/fcm.py`.

1. Группировка аккаунтов по `company_id`; **один** `fetch_company_records` на
   компанию за цикл; результат раскладывается по `staff_id`.
2. `changed_after` — общий на компанию, берётся минимум по её аккаунтам.
3. **Сидирование:** если `record_states` для аккаунта пуста — запрос **без**
   `changed_after` по всему горизонту, состояния записываются, события **не**
   генерируются. Без этого первый дифф выдаст лавину ложных «новых записей».
4. Дифф → запись событий в журнал → отправка push → запись в
   `push_deliveries` и `poll_runs`.
5. Отправка на устройства аккаунта — `asyncio.gather`, не последовательно.
6. **Backoff:** при ошибке по компании пауза 10 с → 30 → 60 → … → 15 мин
   (`backoff_until`, `consecutive_errors`), сброс после первого успеха.
   Иначе упавший аккаунт будет долбиться каждые 10 с и упрётся в лимиты.
7. Ретеншен в конце цикла: `events` и `push_deliveries` — 30 дней,
   `poll_runs` — 7 дней.

**Приёмка:** поменять статус записи в YClients → в логах
`event: CLIENT_CONFIRMED …`, строка в `events`, в `push_deliveries` статус
`sent`. Холостой опрос без изменений → 0 событий, 0 пушей.

### 8.4 Дашборд

**Зачем.** Сейчас состояние сервера — чёрный ящик. Логи через ssh неудобны с
телефона, а именно с телефона чаще всего и захочется глянуть «почему не

**Принцип — тупая серверная страница.** Никакого React, никакой сборки,
никакого npm на Raspberry Pi. FastAPI + Jinja2, один шаблон, обновление через
`<meta http-equiv="refresh" content="10">`. Это осознанно примитивно: такую
страницу невозможно сломать, она не требует обслуживания и работает на любом
телефоне.

**Что на странице** (сверху вниз, одна колонка — под мобильный экран):

1. **Статус**: FCM настроен, аптайм, время последнего опроса, «зелено/красно»
   по последней ошибке.
2. **Лента событий** — последние 50: время, тип, имя клиента, дата и время
   занятия, доставлено на N телефонов. Это главный экран — сюда смотришь,
   когда «не пришло уведомление».
3. **Аккаунты**: компания, специалист, устройств, последний опрос, ошибка,
   backoff.
4. **Устройства**: label, версия приложения, когда последний раз виделись,
   докуда дочитан курсор событий.
5. **Циклы опроса** — последние 20 из `poll_runs`, чтобы видеть длительность и
   не проспать деградацию.

**Авторизация в браузере.** Форма ввода `ADMIN_API_KEY` → HttpOnly Secure
cookie на 30 дней. Заголовок `Authorization` из браузера не отправить, а `?key=`
в адресной строке светит ключ в истории — поэтому cookie. Работает только по
HTTPS, он уже настроен.

**Оценка:** один этап, ~250 строк Python и шаблона.

## 9. Масштабирование

### 9.1 Один запрос на компанию (решено)

Права токена позволяют видеть всех специалистов центра — проверено
пользователем. Поэтому в новом сервисе сразу делается один запрос на компанию
с разбором по `staff_id` в памяти (этап 3). Число специалистов перестаёт влиять
на стоимость опроса, параллелить ничего не нужно.

Если у какой-то компании прав не хватит — фолбэк на поштучный опрос через
`asyncio.gather` с `asyncio.Semaphore(5)`.

### 9.2 Что заложено сразу, чтобы не переделывать

| Что | Где |
|---|---|
| WAL + `busy_timeout` | Этап 2 — иначе `database is locked` при росте устройств |
| Один `Database` на процесс | Этап 2 — в старом пересоздаётся на каждый запрос |
| Один `httpx.AsyncClient` на процесс | Этап 3 — в старом новое TLS-рукопожатие каждые 15 с |
| Backoff по компании | Этап 5 — иначе упавший аккаунт долбится вечно |
| `gather` при отправке на устройства | Этап 5 |
| Индексы и ретеншен | Этапы 2 и 5 |
| Ротация логов Docker | Этап 1 — SD-карта Pi не резиновая |

### 9.3 Много телефонов на один аккаунт

Архитектура ложится сама: журнал событий — **на аккаунт**, курсор — **на
устройство** (`devices.last_ack_event_id`). Каждый телефон догоняет
независимо. Специально ломать это не надо.

## 12. Грабли

1. **`server/` не трогать.** 0.6.9.0 работает через него. Весь новый код —
   в `neiro-push-events/`.

2. **Не возвращать локальный опрос YClients с телефона.** Убирается на
   этапе 8.1 по осознанному решению пользователя. Если кажется, что
   уведомления теряются — чинить надёжность на сервере (журнал + догон).

3. **Не считать `dedupeKey` на сервере.** Только структурные поля; ключ
   выводит приложение своим `SessionSlotKey.build(...)`.

4. **Самопланирующиеся воркеры переставляют себя в `finally`.** Потеря этого
   в `51d8fe3` и была исходным багом. Держать
   `finally { if (!isStopped) scheduleNext(...) }`, не «упрощать» в ранние
   `return`.

5. **Не забыть сидирование состояний** перед первым диффом (этап 5, п. 3).

6. **Устройство регистрируется ровно на одном сервисе.** Если телефон окажется
   зарегистрирован и на старом, и на новом — придут два уведомления.

7. **Сборку Gradle не запускать** — по правилам репозитория
   ([CLAUDE.md](../CLAUDE.md)) её делает пользователь сам.
