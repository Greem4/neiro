# Релизы и самообновление

Пакет документов о том, как Neiro выпускается версиями и как обновляет себя
сама, без магазина и без ручной переустановки по кабелю.

Статус на 13.08.2026: **работает на живом телефоне.** Первый релиз `v0.1.0`
выпущен 11.08.2026, самообновление проверено делом — переходами `0.1.3` →
`0.1.4` → `0.1.5`. Версия и тег поднимаются сами при слиянии PR
([`release-on-merge.yml`](../../.github/workflows/release-on-merge.yml)),
заметки к релизу берутся из `CHANGELOG.md`; 13.08.2026 это сработало вживую —
`0.1.6` вышла от слияния PR без единого ручного шага. Не пройдены только
крайние случаи (подменённая сумма, чужая подпись, Android ниже 12) — [этап 11
TASKS.md](TASKS.md#этап-11--проверка-на-устройстве). Сводная таблица
«[где мы сейчас](TASKS.md#где-мы-сейчас)» — единственное место, где стоят
статусы.

Кроме кода, план покрывает публичное лицо репозитория: лицензия, CONTRIBUTING,
SECURITY, шаблоны issue и PR, CHANGELOG, карточка проекта на GitHub — блок А в
[TASKS.md](TASKS.md#блок-а-публичное-лицо-репозитория). Релиз — первое, что
видит посторонний, и оформление делается до первого тега, а не после.

## Зачем

До всего этого новая версия попадала на телефон одним способом: собрать APK на
Mac, подключить кабель, `adb install`. Пока пользователь один и он же
разработчик — терпимо. Как только приложением пользуется кто-то ещё, схема
разваливается: человек не знает, что вышла новая версия, и не может её
поставить сам.

Что получилось:

1. **Релиз выпускается сам.** Слияние PR в `main` поднимает версию, ставит тег
   и запускает сборку; через несколько минут в GitHub Releases лежит
   подписанный APK, контрольная сумма и список изменений. Тег руками
   (`git tag v0.2.0 && git push origin v0.2.0`) остался запасным путём.
2. **Приложение само замечает новую версию.** Раз в сутки спрашивает GitHub,
   нашло — показывает уведомление.
3. **Обновление ставится по согласию, одним нажатием.** Пользователь жмёт
   «Обновить», приложение качает APK, сверяет сумму и подпись, отдаёт
   системе. Настройки, календарь, архив, токены — на месте.

## Принятые решения

Коротко, чтобы не перечитывать все документы. Обоснование каждого — в
соответствующем файле.

| Решение | Как |
|---|---|
| Канал распространения | GitHub Releases — основной. RuStore планируется позже; сборка из магазина себя не обновляет ([RISKS](RISKS.md#магазин-и-самообновление)) |
| Версия | Начинаем заново с `0.1.0`. Источник — `version.properties`, тег обязан совпадать, CI проверяет ([RELEASE](RELEASE.md#версии)) |
| `versionCode` | Считается из версии: `major * 10000 + minor * 100 + patch`. `0.1.0 → 100` |
| Сборка релиза | GitHub Actions по тегу, ключи и `google-services.json` — в секретах репозитория ([RELEASE](RELEASE.md#секреты)) |
| Проверка обновлений | Раз в сутки, `PeriodicWorkRequest` + проверка при запуске, если давно не спрашивали |
| Установка | `PackageInstaller` Session API. На Android 12+ — без системного диалога (самообновление), ниже и при отказе — обычное подтверждение |
| Проверка целостности | SHA256 из релиза **и** сверка подписи APK с собственной — до установки, не после |
| Новые зависимости | Не нужны: OkHttp, Retrofit, Gson, WorkManager уже в проекте |
| Лицензия | MIT, решено 11.08.2026 ([TASKS](TASKS.md#этап-о1--лицензия-mit)) |
| Пре-релизы | Не используем: все версии пока бета, `release.yml` выпускает обычный релиз |

## Что остаётся неизменным

Правки не должны задеть работающее. Под самообновление **не трогаем**:

- push-уведомления и сервис `neiro-push` — отдельный контур, к релизам
  отношения не имеет;
- синхронизацию YClients, ленту уведомлений, расчёт денег;
- `SessionNotificationCoordinator` и его воркеры — новый воркер живёт
  своей уникальной работой и в чужие цепочки не вмешивается.

Единственные файлы существующего кода, которые придётся изменить, перечислены
в [ARCHITECTURE.md § Точки встраивания](ARCHITECTURE.md#точки-встраивания).
