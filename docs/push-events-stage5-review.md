# Разбор Этапа 5: что не так с поллером и как это чинить

Отчёт по итогам сверки реализации Этапа 5 с [планом](push-events-plan.md).
Составлен 25.07.2026 вечером, анализ — Opus, реализация Этапа 5 — Sonnet.

**Статус: код Этапа 5 закоммичен (`503949a`), правки по этому отчёту НЕ сделаны.**
Всё ниже — разобранные находки и готовые решения, работа начинается с чистого
рабочего дерева.

Порядок работ на завтра — в [§7 «С чего начинать»](#7-с-чего-начинать).

---

## 1. Коротко: что произошло

Этап 5 (поллер + отправка FCM) написан, тесты проходят, сервис поднимается.
Каркас правильный: группировка по компании, один запрос YClients на компанию,
`asyncio.gather` при отправке, числа backoff — всё как в плане.

Но при сверке построчно нашлись **два настоящих бага** и **невыполненный
раздел плана по логам**. Оба бага дают ровно те симптомы, ради лечения которых
весь сервис и затевался:

| Находка | Во что превращается в бою | Приоритет |
|---|---|---|
| [Сидирование сделано не по плану](#21-сидирование-два-источника-правды) | Пачка ложных уведомлений «новая запись» на ровном месте (это П3 из плана) | **блокер** |
| [Состояния пишутся раньше событий](#22-состояния-пишутся-раньше-событий) | Событие теряется навсегда при падении процесса (это П2 из плана) | **блокер** |
| [Логи §8.1 не реализованы](#31-логи-раздела-81-не-реализованы) | «Почему не пришло?» невозможно расследовать | важное |
| [Остальное](#3-важное-но-не-блокеры) | Хрупкость, наблюдаемость | важное |

Почему это проехало незамеченным: Этап 5 реализовал п.3 плана («сидирование»)
**по смыслу**, через уже готовую функцию `derive_events`, не заметив, что
решение «полный запрос или инкрементальный» живёт совсем в другом месте кода и
с сидированием никак не связано. Классический случай из
[CLAUDE.md](../CLAUDE.md): молча выбранное допущение выглядит как выполненная
работа.

## 2. Блокеры

### 2.1 Сидирование: два источника правды

**Где:** [app/poller.py](../neiro-push-events/app/poller.py) — `_poll_company`
(строка ~110) и `_company_changed_after` (строки ~237–241).

**Что требует план.** §7 Этап 5, п.3:

> **Сидирование:** если `record_states` для аккаунта пуста — запрос **без**
> `changed_after` по всему горизонту, состояния записываются, события **не**
> генерируются. Без этого первый дифф выдаст лавину ложных «новых записей».

То есть решение «делать полный запрос или инкрементальный» должно приниматься
**по пустоте `record_states`**.

**Что в коде.** Решение принимается по совершенно другому источнику — по полю
`accounts.changed_after` в БД:

```python
def _company_changed_after(self, accounts: list[WatchedAccount]) -> str | None:
    changed_afters = [a.changed_after for a in accounts]
    if any(c is None for c in changed_afters):
        return None          # → полный запрос
    return min(changed_afters)
```

А сидирование определяется отдельно и позже — внутри `derive_events`, по
пустоте `previous` (то есть `record_states`). **Два независимых источника
правды для одного решения.** Пока они случайно совпадают — всё работает; когда
расходятся — ломается.

**Сценарий А (вероятный): добавили второго специалиста.**

1. Компания 1, аккаунт A (staff=10) работает давно: `changed_after` заполнен,
   `record_states` полна.
2. Регистрируется устройство на нового специалиста → аккаунт B (staff=20),
   `changed_after = NULL`, `record_states` пуста.
3. Следующий цикл: `_company_changed_after([A, B])` видит `None` у B →
   возвращает `None` → **полный запрос по всему горизонту**.
4. Для B это правильно — он сидируется, событий нет. ✅
5. **Для A это катастрофа.** У A непустые `record_states`, поэтому
   `derive_events` работает в обычном режиме диффа. А приходит ему полный
   горизонт — включая записи, которых в его состояниях никогда не было: те,
   что на момент сидирования A лежали за пределами 62-дневного окна и с тех пор
   не менялись (расписание на семестр вперёд — это ровно они). Каждая такая
   запись → **`NEW_BOOKING`**.

Итог: при добавлении специалиста на телефоны прилетает пачка ложных «новая
запись» по чужому давно существующему расписанию.

**Сценарий Б (реже, но злее): `record_states` пуста при заполненном `changed_after`.**

Бывает после восстановления из бэкапа, ручной чистки таблицы или сбоя записи.
Тогда:

1. `changed_after` заполнен → запрос **инкрементальный**, придут 2–3
   изменившиеся записи.
2. `record_states` пуста → `derive_events` считает это сидированием и
   записывает базовый снимок **из этих 2–3 записей**.
3. Следующий цикл: всё остальное расписание приходит как незнакомые
   `record_id` → **`NEW_BOOKING` на весь календарь**.

**Решение (выбрано пользователем 25.07.2026): сидирование — свойство цикла
компании, а не отдельного аккаунта.**

Если хоть у одного аккаунта компании `record_states` пуста — весь цикл идёт
полным запросом, и события **не генерируются ни для одного аккаунта компании**.

Цена: реальные изменения, случившиеся именно в этот цикл у уже работающих
аккаунтов, будут пропущены — они молча уедут в состояния. Ситуация редкая
(добавление специалиста, восстановление из бэкапа), и пропустить один цикл
лучше, чем выдать лавину ложных уведомлений.

**Что писать:**

1. В [app/database.py](../neiro-push-events/app/database.py) — лёгкая проверка
   без выгрузки всех состояний:

```python
def has_record_states(self, account_id: int) -> bool:
    with self.connect() as conn:
        row = conn.execute(
            "SELECT 1 FROM record_states WHERE account_id = ? LIMIT 1",
            (account_id,),
        ).fetchone()
    return row is not None
```

2. В [app/events.py](../neiro-push-events/app/events.py) — обновление состояний
   без генерации событий:

```python
def merge_states(
    previous: dict[int, RecordState],
    records: list[YClientsRecord],
) -> dict[int, RecordState]:
    """Сидирование: состояния обновляются, события не генерируются (§7 Этап 5 п.3)."""
    states = dict(previous)
    for record in records:
        states[record.record_id] = _state_from_record(record)
    return states
```

3. В `_poll_company` — решение принимается один раз, на всю компанию:

```python
seeding = any(not self._db.has_record_states(a.id) for a in active_accounts)
changed_after = None if seeding else self._company_changed_after(active_accounts)
```

и дальше `seeding` прокидывается в `_poll_account`, где вместо `derive_events`
вызывается `merge_states`.

**Что НЕ трогать.** `derive_events` и `should_seed_baseline` оставить как есть:
внутренняя проверка «пустой `previous` → событий нет» остаётся страховкой на
случай, если поллер когда-нибудь ошибётся. Все 14 тестов
`tests/test_events.py` должны продолжать проходить без правок — если какой-то
упал, значит правка задела чистый дифф, чего быть не должно.

### 2.2 Состояния пишутся раньше событий

**Где:** [app/poller.py](../neiro-push-events/app/poller.py) — `_poll_account`,
строки ~167–174.

```python
previous_states = self._db.get_record_states(account.id)
events, new_states = derive_events(previous_states, records)
self._db.replace_record_states(account.id, new_states)   # ← состояния

if not events:
    return 0, 0

event_ids = self._db.insert_events(account.id, events)   # ← журнал
```

**Почему это баг.** Между этими двумя записями процесс может умереть —
рестарт контейнера, деплой, OOM на Pi, `docker compose down` в неудачный
момент. Тогда состояния уже сдвинуты, а события в журнал не попали. Следующий
цикл сравнит новые записи с уже обновлёнными состояниями, разницы не увидит —
и **событие потеряно навсегда**.

Это буквально П2 из [плана §3](push-events-plan.md), ради которого весь сервис
и строится:

> **П2. Потерянный push = потерянное событие навсегда.** […] Главный риск.

Журнал событий — единственная гарантия догона (§5.2, три независимых пути
доставки). Если он теряет записи, разваливается вся конструкция: догон по
курсору не найдёт того, чего в журнале нет.

**Решение: поменять порядок — сначала журнал, потом состояния.**

```python
if events:
    event_ids = self._db.insert_events(account.id, events)
self._db.replace_record_states(account.id, new_states)
```

При падении между ними теперь получится обратное: состояния не сдвинулись,
следующий цикл сгенерирует те же события повторно → в журнале дубль. Это
**безопасный** отказ: дубли гасит `wasEventNotified(dedupeKey)` в приложении
(LRU на 300 ключей,
[SessionNotificationPreferences.kt:117](../app/src/main/java/ru/greemlab/neiro/notifications/SessionNotificationPreferences.kt#L117),
см. [план §5.2](push-events-plan.md)). Потеря — невосстановима, дубль —
гасится штатно.

**Идеально** было бы писать событие и состояния одной транзакцией, но сейчас
`Database` выдаёт соединение на каждый метод (`with self.connect()`), так что
это потребует нового метода вида `commit_poll_result(account_id, events,
states)` с одним `conn`. Если делать — то этим же коммитом; если нет —
перестановка порядка закрывает основную часть риска.

## 3. Важное, но не блокеры

### 3.1 Логи раздела §8.1 не реализованы

План §8.1 перечисляет четыре строки, которые должен писать поллер. Факт:

| Строка из §8.1 | Есть? | Где |
|---|---|---|
| `INFO poll company=123 records=3 events=1 pushes=2 duration=412ms` | ❌ **нет** | цифры считаются и пишутся в `poll_runs`, но в лог не выводятся |
| `INFO event id=1234 CLIENT_CONFIRMED "Иванов Ваня" 2026-07-26 15:00 → 2 devices` | ⚠️ частично | `_poll_account`, стр. ~176: нет `→ N devices`, нет кавычек вокруг имени |
| `WARN push failed device=… : UNAVAILABLE` | ✅ есть | `_push_to_device`, стр. ~219 |
| `INFO backoff company=123 until=12:41:05 (errors=3)` | ❌ **нет** | backoff проставляется молча |

Почему это не косметика: «Прозрачность» — одна из четырёх жёстких рамок
[§1 плана](push-events-plan.md), а §9.3 («что делать, если уведомление не
пришло») построен на том, что по логам видно, шёл ли опрос и не сидит ли
аккаунт в backoff. Сейчас backoff невидим полностью.

Для строки про событие нужно переставить логирование **после** получения
списка устройств — сейчас оно выше, и числа устройств в этот момент ещё нет.

### 3.2 Все аккаунты в backoff → тихий выход

`_poll_company`, стр. ~105–106:

```python
active_accounts = [a for a in accounts if not self._is_backed_off(a, now)]
if not active_accounts:
    return          # ни лога, ни записи в poll_runs
```

В дашборде (Этап 7) и в `poll-log` это выглядит как «опрос просто перестал
происходить», без единого следа почему. Надо либо писать строку в `poll_runs`,
либо логировать — но не каждые 10 секунд, иначе лог зальёт (например, писать
только при первом попадании в backoff, что и так делает строка из §8.1).

### 3.3 Статус `nudged` вне контракта

`_push_to_device`, стр. ~232: `status = "nudged" if result.nudged else "sent"`.

План §7 Этап 2 задаёт контракт колонки явно:

```sql
status TEXT NOT NULL,          -- sent | failed | token_invalid
```

Причём в реализации схемы
([app/database.py](../neiro-push-events/app/database.py), стр. ~140) этот
поясняющий комментарий **потерян ещё на Этапе 2** — значит следующий, кто
полезет в схему, вообще не узнает, какие значения допустимы. Этап 5 сверху
добавил четвёртый статус, не описанный нигде.

Дашборд (Этап 7) и §9.3 будут разбирать эту колонку — расхождение вылезет там.

**Решение:** писать `status="sent"`, а факт нуджа складывать в `detail`
(например `"nudged: payload > 3KB"`). Нудж — это успешная отправка, просто без
payload; отдельным статусом он быть не должен. Заодно вернуть комментарий
`-- sent | failed | token_invalid` в схему.

### 3.4 `_poll_account` не обёрнут в `try`

`_poll_company`, стр. ~146–157: цикл по аккаунтам вызывает `_poll_account` без
защиты. Любое исключение внутри (ошибка SQLite, битые данные) прерывает
обработку **всей компании**: оставшиеся аккаунты пропускаются, `changed_after`
им не обновляется, `record_poll_run` не пишется вообще.

Асимметрия: вокруг `fetch_company_records` `try` есть, вокруг обработки — нет.

**Решение:** обернуть вызов, ошибку писать в `last_error` конкретного аккаунта
и продолжать цикл по остальным.

### 3.5 Токен берётся у произвольного аккаунта

`_poll_company`, стр. ~113:

```python
lead_account = active_accounts[0]
partner_token = self._secret_box.decrypt(lead_account.partner_token_enc)
```

Запрос на всю компанию идёт с токеном **первого попавшегося** аккаунта (порядок
по `id`). Если именно у него токен протух, падает опрос всей компании — включая
аккаунты с живыми токенами, которые могли бы отработать.

План §9.1 предусматривает фолбэк («если у какой-то компании прав не хватит —
фолбэк на поштучный опрос»), он не реализован — и это нормально, план говорит
«если не хватит». Но молчаливое допущение «токен любого аккаунта подойдёт»
стоит хотя бы записать комментарием, а при ошибке — пробовать следующий
аккаунт компании, прежде чем валить всю компанию в backoff.

### 3.6 FCM не настроен → спам `failed`

[app/fcm.py](../neiro-push-events/app/fcm.py): `send_events_push` кидает
`RuntimeError`, если FCM не сконфигурирован. `_push_to_device` ловит любое
исключение и пишет `failed` — **на каждое событие каждого устройства каждый
цикл**. За сутки это тысячи мусорных строк в `push_deliveries`, и настоящие
сбои доставки в них утонут.

Старый сервис ([server/app/poller.py](../server/app/poller.py)) проверял это
явно и клал внятное сообщение в `last_error` аккаунта. Здесь так же: проверить
`self._fcm.is_configured` до отправки, один раз на аккаунт.

## 4. Тесты: чего не хватает

`tests/test_poller.py` содержит 4 теста, все проходят. Но два **явных пункта
приёмки** не покрыты:

| Пункт | Откуда | Есть? |
|---|---|---|
| «Холостой опрос без изменений → 0 событий, 0 пушей» | приёмка Этапа 5 + §11 («проверка, что П3 вылечен») | ❌ нет |
| «Обрыв сети → backoff растёт, **после восстановления сбрасывается**» | §11 | ⚠️ проверено только что backoff блокирует следующий цикл; ни рост `consecutive_errors`, ни сброс после успеха не проверяются |

Плюс после правок понадобятся новые:

- сидирование на уровне компании: аккаунт с полными состояниями + новый пустой
  аккаунт в одной компании → **ноль** событий у обоих (тест на находку 2.1,
  сценарий А);
- события попадают в журнал раньше состояний (тест на находку 2.2 — проще
  всего проверить через порядок вызовов на фейковом `Database`).

## 5. Наблюдения на будущее (не трогать сейчас)

Не баги и не входят в Этап 5 — записано, чтобы не потерялось.

**5.1. `record_states` растёт бесконечно.** Ретеншена для этой таблицы нет ни в
плане, ни в коде. Записи с давно прошедшими датами остаются в состояниях
навсегда. За год работы это тысячи строк, которые целиком выгружаются
`get_record_states` **на каждый аккаунт каждые 10 секунд**. Стоит подумать об
очистке по `date < today - N` — но это меняет поведение диффа, так что не
походя.

**5.2. Ретеншен `events` 30 дней против курсора устройства.** Если телефон не
выходил на связь 31 день, его `last_ack_event_id` указывает на уже удалённое
событие. Догон отдаст всё, что после этого id — то есть весь журнал → лавина
уведомлений при первом запуске. **Учесть в Этапе 6** при написании
`GET /v1/devices/{id}/events`: если курсор устройства меньше минимального `id` в
журнале, отдавать не всё подряд, а сбрасывать курсор на текущий максимум.

**5.3. Блокирующий SQLite внутри `async`.** Все вызовы `self._db.*` —
синхронный `sqlite3` в корутинах. `asyncio.gather` при отправке на устройства
даёт настоящую параллельность только HTTP-запросам к FCM (это главное), а вот
записи в БД выполняются последовательно и на время выполнения блокируют event
loop. Плюс `record_push_delivery` открывает **отдельное соединение на каждую
пару событие×устройство**. Не регресс (старый сервис устроен так же) и на
текущих объёмах несущественно, но при росте числа устройств это первое, что
упрётся.

**5.4. Ретеншен каждые 10 секунд — осознанно оставлено.** `purge_old_data()`
вызывается каждый цикл, то есть 8640 раз в сутки, тремя `DELETE` с
`datetime('now', …)`, причём индексов на `events.created_at` и
`push_deliveries.created_at` нет — это фулсканы. Предлагалось снизить до раза в
час и добавить индексы; **пользователь решил 25.07.2026 оставить как в плане**
(§7 Этап 5, п.7 — «ретеншен в конце цикла»). Зафиксировано, чтобы при будущих
тормозах на Pi было понятно, что это известный компромисс, а не недосмотр.

## 6. Что в Этапе 5 сделано правильно

Чтобы при правках это не сломать:

- группировка аккаунтов по `company_id` и **один** `fetch_company_records` на
  компанию за цикл (§7 Этап 5 п.1) — раскладка по `staff_id` в памяти;
- `changed_after` общий на компанию, берётся минимум по аккаунтам (п.2);
- `asyncio.gather` при отправке на устройства аккаунта (п.5);
- шаги backoff `10 → 30 → 60 → 120 → 300 → 600 → 900` и сброс счётчика после
  успешного опроса (п.6) — числа соответствуют плану;
- разделение чистого диффа (`events.py`, без БД и сети) и I/O (`poller.py`) —
  благодаря этому 14 тестов Этапа 4 остаются валидными и после правок;
- `PollService` собирается один раз в `lifespan`, один `Database` и один
  `httpx.AsyncClient` на процесс, клиент закрывается при остановке
  (§9.2 «что заложено сразу»).

### Как гонять тесты

`pytest` в проекте не установлен и в `requirements.txt` его нет — окружение
собирается разово во временном каталоге:

```bash
python3 -m venv /tmp/venv-neiro-events
/tmp/venv-neiro-events/bin/pip install pytest httpx pydantic-settings \
    google-auth cryptography requests fastapi jinja2
cd neiro-push-events && PYTHONPATH=. /tmp/venv-neiro-events/bin/python -m pytest tests/ -v
```

Сборку Gradle не запускать — по [CLAUDE.md](../CLAUDE.md) её делает пользователь.
