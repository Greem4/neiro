## Где мы сейчас

Этапы 0–7 **закрыты полностью**, включая обе сверки с планом по 1–5:

- **Этапы 1–4** — два блокера (`date` со временем, дифф не различал
  удаление/отмену/возврат) плюс находки в FCM. Все четыре коммита из
  [stage1-4-review.md](stage1-4-review.md) сделаны.
- **Этап 5** — два блокера в поллере (сидирование, порядок записи) плюс
  находки по логам/устойчивости. Все шесть коммитов из
  [stage5-review.md](stage5-review.md) сделаны.
- **Этап 6** — API регистрации и догона (§6.2 плана): `POST
  /v1/devices/register`, `DELETE /v1/devices/{id}`, `GET
  /v1/devices/{id}/events` (горизонт §6.4 + точный `has_more`), `POST
  /v1/devices/{id}/events/ack`, богатый `/health`. 9 новых тестов в
  `tests/test_main.py`.
- **Этап 7** — дашборд (§8.4 плана): `/dashboard` (HTML, cookie-логин по
  admin-ключу), `/v1/admin/dashboard.txt` (тот же снимок текстом),
  `/v1/admin/events`, `/v1/admin/poll-log`, `scripts/dash.sh` для терминала.
  10 новых тестов в `tests/test_main.py`.
- **Этап 8** — правки приложения ([app.md](app.md)), пять коммитов A–D (см.
  таблицу ниже). Локальный опрос убран, показ и правка календаря идут прямо
  из payload, догон по курсору `last_event_id` закрывает пропуски push'а,
  `local.properties` и версия обновлены под новый сервис.

**Ничего из этого ещё не задеплоено на Pi** — все коммиты только в
локальной ветке `фикс-уведомлений`. Дальше — Этап 9 (документация по факту,
§7.9 плана), затем деплой.

**Не забыть при выкатке:** перед первым запуском после этих правок выполнить
`DELETE FROM record_states;` — иначе первый же цикл выдаст `RESCHEDULED` на весь
календарь, потому что старые состояния хранят дату вместе с временем.

## Подводные камни

Находки, которые не входили в изначальный план, но всплыли по ходу. По правилу
«расходится с реальностью — остановись и спроси» ([CLAUDE.md](../../CLAUDE.md))
каждая сначала обсуждалась с пользователем.

### 1. `backup.sh` никогда не бэкапил `.env`

`docker compose exec -T neiro-push rm -f ...` без `< /dev/null` наследовал
stdin от родительского скрипта и съедал из него весь хвост — строки `cp .env
...` и далее просто не выполнялись, без единой ошибки в выводе. Бэкап базы
работал, бэкап секретов — никогда. Исправлено в
[server/scripts/backup.sh](../../server/scripts/backup.sh) (коммит `3a17298`)
добавлением `< /dev/null`.

### 2. Реальная топология сети разошлась с планом

План (§5.1 и §7 Этап 1) предполагал маршрутизацию `/v2/*` через Caddy на Pi
(`handle_path` рядом с существующим `reverse_proxy neiro-push:8010`). В
реальности `push.neiro.greemlab.ru` обслуживается иначе: VPS nginx
(`roster-vps`, `176.12.65.86`) → `proxy_pass` на локальный порт → отдельный
reverse SSH-туннель Pi→VPS → сервис на Pi. Caddy в этом пути не участвует
вообще. По признанию пользователя, туннель на своё время был «повешен не на тот
сервис» — собственно поэтому весь новый сервис событий и затевался.

Вместо `handle_path` в Caddy сделано:

- независимый reverse-туннель под `neiro-push-events`: systemd `--user` юнит
  `neiro-push-events-tunnel.service` на Pi, порт **18082** (VPS) →
  `127.0.0.1:8011` (Pi) —
  [scripts/start-tunnel.sh](../../neiro-push-events/scripts/start-tunnel.sh),
  [scripts/install-tunnel.sh](../../neiro-push-events/scripts/install-tunnel.sh);
- `location /v2/` в nginx на VPS, идемпотентно —
  [scripts/patch-vps-nginx-v2.sh](../../neiro-push-events/scripts/patch-vps-nginx-v2.sh);
- [scripts/patch-pi-caddy-v2.py](../../neiro-push-events/scripts/patch-pi-caddy-v2.py)
  **написан, но не используется** — оставлен как задокументированная попытка «по
  плану», которая не подошла; можно удалить на Этапе 9, если не найдётся
  применения.

### 3. Побочная находка: маршрут `neiro-push` в Caddy жил только в памяти процесса

Не связано с новым сервисом, но критично для уже работающего. У Caddy на Pi
отключён admin API (`admin off` в Caddyfile) — значит `caddy reload` не может
достучаться и не применяет изменения файла; конфиг живёт в памяти процесса с
последнего рестарта. Блок `http://push.neiro.greemlab.ru { reverse_proxy
neiro-push:8010 }` **отсутствовал в файле на диске** (видимо, потерян при
правках для другого проекта на этом же Caddy), но продолжал отвечать из памяти —
то есть был бы молча потерян при любом следующем рестарте контейнера, включая
обычный `server/scripts/deploy.sh` (он сам вызывает `caddy reload` как часть
штатного деплоя).

Восстановлено штатным
[server/scripts/patch-pi-caddy.py](../../server/scripts/patch-pi-caddy.py) (тем же
скриптом, что изначально создавал этот блок) + `docker compose restart caddy`.
Резервная копия файла до правки лежит на Pi:
`~/server/caddy/Caddyfile.before-restore-<timestamp>`. Проверено вручную: старый
`/health` и чужой `medicine.greemlab.ru` (другой проект на том же Caddy) оба
живы после рестарта.

### 4. Курсор `next_changed_after` не входил в Этап 3

[app/yclients.py](../../neiro-push-events/app/yclients.py) на Этапе 3 разбирал
записи, но не считал курсор для следующего опроса — в плане эта функция явно не
расписана, а поллеру она нужна. Добавлена как `next_changed_after()` в тот же
файл (по образцу
[server/app/yclients.py:106](../../server/app/yclients.py#L106)), аддитивно —
код разбора записей не тронут.

### 5. Синглтон `get_poll_service()` из старого сервиса не подошёл

Первый черновик `poller.py` копировал паттерн старого сервиса — модуль-level
синглтон, который сам создаёт свой `Database`. Это дало бы **второй** экземпляр
`Database` на процесс (первый уже держит `main.py` в `app.state.db`) — прямое
нарушение принципа Этапа 2 «один `Database` на процесс». Убрано: `PollService`
собирается один раз в `lifespan` вместе с общим `Database`, `SecretBox`,
`YClientsClient`, `FcmSender`; `YClientsClient.aclose()` вызывается при
остановке — раньше эта функция (написанная в Этапе 3) нигде не вызывалась.

### 6. `client_name` собирался в неправильном порядке полей

Найдено на пересечении с [app.md §2.2](app.md) —
документом, который параллельно уточнял пользователь: контракт требует ровно
`displayName ?: (name + " " + surname)`, как в `extractClientName`
([YClientsCalendarSync.kt:700](../../app/src/main/java/ru/greemlab/neiro/sync/YClientsCalendarSync.kt#L700)).
[app/yclients.py](../../neiro-push-events/app/yclients.py) на Этапе 3 собирал
`surname + name + patronymic` — другой порядок и лишнее поле. Разница меняет
`dedupeKey` в приложении и превращается в молчаливые дубли уведомлений. Исправлено
коммитом `ba75934`, проверено на синтетической записи.

### 7. Этап 5 разошёлся с планом по сидированию и порядку записи

Самая крупная находка, вынесена в отдельный документ:
**[stage5-review.md](stage5-review.md)**. Кратко: два
блокера (ложные `NEW_BOOKING` из-за рассинхрона решения о сидировании; риск

### 8. Этап 3 остался без тестов, и в парсинге нашлись баги

Обнаружено 26.07.2026 при сплошной сверке Этапов 1–4. `tests/test_yclients.py`
не существует вовсе: 14 тестов Этапа 4 конструируют `YClientsRecord` вручную и
парсер не трогают. Через эту дыру прошли **два** бага подряд — сначала порядок
полей в `client_name` (камень 6, коммит `ba75934`), теперь формат `date`.

`date` берётся из поля `date` ответа YClients как есть, а там лежит
`"2026-06-28 18:00:00"` — дата **вместе с временем**, проверено по реальному
экспорту в репозитории. Контракт §6.1 требует `YYYY-MM-DD`. Дифф от этого не
страдает (строки сравниваются между собой), ломается контракт наружу — в
приложение уедет неразбираемая дата.

Плюс две находки в FCM: OAuth-токен обновляется синхронным сетевым вызовом на
каждую отправку прямо в event loop, и `INVALID_ARGUMENT` трактуется как мёртвый
токен, из-за чего живое устройство может быть удалено из базы навсегда.

Разбор и порядок правок — **[stage1-4-review.md](stage1-4-review.md)**. Все
четыре коммита сделаны.
