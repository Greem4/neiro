## 2. Блокер: `date` уезжает со временем

**Где:** [app/yclients.py:121](../../neiro-push-events/app/yclients.py#L121),
`_parse_record`.

```python
date=str(raw.get("date") or ""),
time=_extract_time(raw.get("datetime")),
```

**В чём дело.** `time` аккуратно вытаскивается подстрокой из `datetime`, а
`date` берётся из поля `date` как есть. Но в YClients поле `date` — это **дата
и время визита**, а не дата. Проверено по реальному ответу API, сохранённому в
репозитории:

```jsonc
// tools/yclients-sandbox/exports/520135-2026-06-28.json:1397
"date": "2026-06-28 18:00:00",
"datetime": "2026-06-28T18:00:00+03:00",
```

Контракт [плана §6.1](plan.md) требует другого:

| Поле | Тип | Формат |
|---|---|---|
| `date` | string | `YYYY-MM-DD` |

**Во что превращается.** Событие уезжает в push как
`"date": "2026-06-28 18:00:00"`. Дальше:

- **Этап 8 не соберёт `TrackedSession`.** `PushSessionEvent.toSessionEvent()`
  будет писаться под контракт, то есть под `LocalDate.parse(date)` — на строке
  с временем это исключение. Приложение либо уронит разбор, либо молча
  выбросит событие.
- **`prev_date` в `RESCHEDULED`** уезжает в том же виде.
- **`slotKey` разъедется**, а на нём держится вся защита от дублей.

Существующий разбор в приложении
([YClientsCalendarSync.kt:682](../../app/src/main/java/ru/greemlab/neiro/sync/YClientsCalendarSync.kt#L682)
`parseRecordDate`) такую строку пережёвывает — там есть ветка под
`yyyy-MM-dd HH:mm:ss` и фолбэк `take(10)`. **Но это не оправдание.** Тот парсер
разбирает ответы YClients напрямую, а новый путь идёт по контракту §6.1, и
подпирать сервер снисходительностью клиента — ровно то, из-за чего появился
баг с `client_name` (`ba75934`).

**Сам дифф этот баг не ломает:** `derive_events` сравнивает состояния между
собой, обе строки в одном формате. Поэтому 14 тестов Этапа 4 и не покраснели.
Ломается контракт наружу.

**Решение: брать дату оттуда же, откуда время — из `datetime`.**

Это прямо следует из [app.md §2.1](app.md): приложение берёт локальное время
подстрокой из `datetime`, без пересчёта часового пояса. Дата обязана
приезжать из того же источника, иначе на границе суток они разойдутся между
собой.

**Что писать** в [app/yclients.py](../../neiro-push-events/app/yclients.py) —
новая функция рядом с `_extract_time`:

```python
def _extract_date(datetime_value: str | None, date_value: str | None) -> str:
    """`YYYY-MM-DD` подстрокой, без пересчёта часового пояса (app.md §2.1).

    Основной источник — `datetime` (`2026-06-28T18:00:00+03:00`), тот же, из
    которого берётся `time`: иначе на границе суток дата и время разъедутся.
    Фолбэк — поле `date`, которое YClients отдаёт как `2026-06-28 18:00:00`,
    то есть с временем: от него берутся первые 10 символов.
    """
    for value in (datetime_value, date_value):
        if not value:
            continue
        head = value[:10]
        if len(head) == 10 and head[4] == "-" and head[7] == "-":
            return head
    return ""
```

и вызов в `_parse_record`:

```python
date=_extract_date(raw.get("datetime"), raw.get("date")),
```

**Почему проверка на дефисы, а не `split`.** Формат приходит от внешнего API;
если он однажды изменится, лучше вернуть пустую строку, чем молча положить в
контракт мусор. Пустая дата видна сразу, кривая — всплывёт через неделю.

**Что НЕ трогать.** `_extract_time` оставить как есть — она уже соответствует
[app.md §2.1](app.md) и проверена. Поле `date` из `YClientsRecord` не удалять и
не переименовывать: на него завязан `events.py` и все 14 тестов.

### 2.1 Обязательно: сбросить `record_states` после этой правки

**Это часть той же работы, пропустить нельзя.**

`record_states` хранит `date` в старом формате — со временем. После правки
парсер начнёт отдавать `2026-06-28`, а в состояниях лежит
`2026-06-28 18:00:00`. Для `derive_events` это **разные значения**, то есть
изменение даты у **каждой** записи разом:

```
old.date "2026-06-28 18:00:00" != "2026-06-28" new.date  →  RESCHEDULED
```

Итог без сброса: лавина `RESCHEDULED` на весь календарь в первый же цикл после
деплоя — на все телефоны сразу.

Сервис в работу не введён, боевых данных в базе нет, поэтому решение простое:
**удалить содержимое `record_states` при выкатке**, сервис пересидируется сам
(пустые состояния → сидирование, события не генерируются — это как раз то, что
чинится в [stage5-review §2.1](stage5-review.md#21-сидирование-два-источника-правды)).

Миграцию в код писать **не нужно** — одноразовое действие при деплое:

```sql
DELETE FROM record_states;
```

Записать это в сообщение коммита нельзя (одна строка по
[CLAUDE.md](../../CLAUDE.md)), поэтому **добавить пункт в
[progress.md](progress.md)**: «после выкатки правки `date` очистить
`record_states`». Пользователю сказать об этом прямо при сдаче работы.

## 3. Важное

### 3.1 OAuth-токен обновляется на каждую отправку

**Где:** [app/fcm.py:110–114](../../neiro-push-events/app/fcm.py#L110-L114).

```python
def _access_token(self) -> str:
    assert self._credentials is not None
    request = google.auth.transport.requests.Request()
    self._credentials.refresh(request)
    return self._credentials.token
```

`refresh()` — это **сетевой запрос к `oauth2.googleapis.com`, синхронный**
(`google.auth.transport.requests` построен на `requests`, не на `httpx`). Он
вызывается из `send_events_push`, то есть из корутины, и на время запроса
**блокирует весь event loop**: ни опрос, ни другие отправки в этот момент не
идут.

Сколько раз: один на каждое устройство на каждый цикл с событиями.
`asyncio.gather` по устройствам не помогает — блокирующий вызов
распараллелиться не может, они выстроятся в очередь.

Токен Google живёт час. То есть 99,9% этих запросов не нужны.

**Решение: обновлять только когда токен реально протух.**

```python
def _access_token(self) -> str:
    assert self._credentials is not None
    # refresh() — синхронный сетевой вызов, блокирует event loop.
    # Токен живёт час, поэтому ходим в Google только когда он протух.
    if not self._credentials.valid:
        request = google.auth.transport.requests.Request()
        self._credentials.refresh(request)
    return self._credentials.token
```

`Credentials.valid` — штатное свойство `google-auth`: `True`, если токен есть и
не истёк (библиотека держит запас перед фактическим истечением, отдельно
вычитать ничего не надо).

**Так же устроено в старом сервисе?** Нет — там
([server/app/fcm.py:108](../../server/app/fcm.py#L108)) тот же безусловный
`refresh`. Это не регресс, а унаследованное поведение. Но старый сервис слал
пуши редко, а новый работает каждые 10 секунд, поэтому терпимое становится
заметным. **Старый сервис при этом не трогать** — он работает, правка только в
новом.

### 3.2 `INVALID_ARGUMENT` удаляет живое устройство

**Где:** [app/fcm.py:101 и 106](../../neiro-push-events/app/fcm.py#L101).

```python
if status in {"NOT_FOUND", "UNREGISTERED", "INVALID_ARGUMENT"}:
    return True
```

Дальше в поллере ([poller.py:224–230](../../neiro-push-events/app/poller.py#L224-L230))
`token_invalid` означает `delete_device(device_id)` — **устройство удаляется из
базы навсегда**.

**Почему это опасно.** `UNREGISTERED` и `NOT_FOUND` действительно значат
«токен мёртв, приложение удалено». А `INVALID_ARGUMENT` FCM возвращает и на
**некорректный запрос**: неподходящее поле в `message`, слишком большой
payload, кривой формат `data`. То есть на **нашу собственную ошибку**.

Сценарий: правка Этапа 6 или 8 добавляет в payload поле, которое FCM не
принимает → `INVALID_ARGUMENT` на каждое устройство → за один цикл из базы
исчезают **все** телефоны. Уведомления не приходят, в логах «invalid FCM
token», причина выглядит как проблема на стороне телефонов. Восстановление —
только перерегистрацией каждого устройства вручную.

**Решение: удалять только по `UNREGISTERED` и `NOT_FOUND`.**

```python
def _is_invalid_token_error(self, response: httpx.Response) -> bool:
    """Токен мёртв — устройство можно удалять.

    INVALID_ARGUMENT сюда НЕ входит: FCM отдаёт его и на нашу собственную
    ошибку в теле сообщения, а не только на мёртвый токен. Удалять по нему
    устройство — значит терять живые телефоны из-за своей же опечатки.
    """
    try:
        payload = response.json()
    except json.JSONDecodeError:
        return response.status_code in {404, 410}
    error = payload.get("error", {})
    status = str(error.get("status", "")).upper()
    if status in {"NOT_FOUND", "UNREGISTERED"}:
        return True
    details = error.get("details", [])
    for item in details:
        error_code = str(item.get("errorCode", "")).upper()
        if error_code == "UNREGISTERED":
            return True
    return response.status_code in {404, 410}
```

`INVALID_ARGUMENT` после этого попадает в общую ветку — `RuntimeError` с текстом
ответа, поллер запишет `failed` в `push_deliveries` и залогирует. Событие
никуда не денется: устройство подберёт его догоном (Этап 6). Именно так и
должно быть — ошибка формата обязана быть видной и чиниться нами, а не молча
списываться на телефон.

**Осознанное расхождение со старым сервисом.** Там
([server/app/fcm.py:96](../../server/app/fcm.py#L96)) `INVALID_ARGUMENT` в
списке. Это его баг, который в новом сервисе не воспроизводим. Старый **не
править**.

### 3.3 Дифф не различает удаление, отмену и возврат

**Приоритет: блокер.** Стоит в §3 только чтобы не ломать ссылки на соседние
разделы; делается вторым коммитом, сразу после даты.

**Где:** [app/events.py:57–117](../../neiro-push-events/app/events.py#L57-L117),
`derive_events`.

Три отдельные проблемы в одном месте, все — про то, какие уведомления увидит
специалист.

#### Что означают отмена и удаление

Разница принципиальная, подтверждена пользователем 26.07.2026:

| Действие в YClients | Что это значит | Событие |
|---|---|---|
| `attendance = -1` | клиент **не пришёл сегодня**, запись остаётся | `CANCELLED` |
| `deleted = 1` | клиент **не придёт больше никогда**, записи нет | `DELETED` |

Это две разные новости, и специалисту нужны обе. Схлопывать их в одно событие
нельзя.

Так же устроено и в приложении, где эта логика работает и всех устраивает:
запись, исчезнувшая из календаря, даёт `DELETED`
([SessionChangeDetector.kt:51](../../app/src/main/java/ru/greemlab/neiro/notifications/SessionChangeDetector.kt#L51)),
а запись со статусом «отменён» — `CANCELLED`
([строка 52](../../app/src/main/java/ru/greemlab/neiro/notifications/SessionChangeDetector.kt#L52)).

#### Проблема 1: разбор не обрывается

Проверки в `derive_events` идут подряд, без `continue`. Запись пришла с
`deleted = 1` — сгенерировался `DELETED`, и дальше по той же записи проверяются
`CANCELLED`, `RESCHEDULED`, `CLIENT_CONFIRMED`, `CLIENT_ARRIVED`. Если YClients
при удалении заодно ставит `attendance = -1`, в журнал уедут **два события об
одном действии**, и на телефон придут два уведомления про запись, которой уже
нет.

Приложение так не делает: при отмене оно ставит событие и сразу `continue`
([SessionChangeDetector.kt:61–66](../../app/src/main/java/ru/greemlab/neiro/notifications/SessionChangeDetector.kt#L61-L66)).
Сервер обязан вести себя так же.

Отдельный случай: запись **уже была** удалена (`old.deleted = 1`) и продолжает
приходить в выдаче с `with_deleted=1`. Сейчас по ней может сработать
`RESCHEDULED`, если у удалённой записи поменяли дату. События по удалённой
записи не нужны вообще.

#### Проблема 2: возврат записи молчит

Запись удалили, потом вернули (`deleted` из `1` в `0`). Или отменили, потом
сняли отмену (`attendance` из `-1` в `0`).

Прогон по текущему коду: ветка `DELETED` требует `record.deleted and not
old.deleted` — не сработает. Ветка `CANCELLED` требует `record.attendance ==
-1` — не сработает. `CLIENT_CONFIRMED`/`CLIENT_ARRIVED` требуют `2` и `1` — не
сработают. `NEW_BOOKING` живёт в ветке `old is None`, а у вернувшейся записи
состояние сохранилось.

**Итог: ноль событий.** Запись вернулась в расписание, специалист об этом не
узнал.

А приложение об этом сообщает — и обоими путями: снятие отмены даёт
`NEW_BOOKING` ([строка 71](../../app/src/main/java/ru/greemlab/neiro/notifications/SessionChangeDetector.kt#L71)),
вернувшаяся в календарь запись — тоже `NEW_BOOKING`
([строка 45](../../app/src/main/java/ru/greemlab/neiro/notifications/SessionChangeDetector.kt#L45)).
То есть после переезда на серверные события вы бы **потеряли** уведомление,
которое сейчас приходит.

**Решение (выбрано пользователем 26.07.2026): возврат записи — это
`NEW_BOOKING`.** Новый тип события **не заводить**.

Почему не новый тип: `SessionEventType` в приложении пришлось бы расширять, а
за ним — флаг в `SessionNotificationPreferences`, переключатель на экране
настроек, тексты, строки ресурсов и правку работающего
`SessionChangeDetector`. И главное, пути доставки разъехались бы: сервер слал
бы `RESTORED`, локальный дифф — `NEW_BOOKING`, тип входит в `dedupeKey`, и одно
возвращение записи показалось бы **двумя** уведомлениями. С `NEW_BOOKING` оба
пути говорят одно и то же, ключи совпадают, дубль гасится штатно.

#### Что писать

Полный порядок разбора одной записи. Порядок веток — часть решения, менять
нельзя: удаление сильнее отмены, возврат проверяется **до** обычных изменений.

```python
for record in records:
    old = previous.get(record.record_id)

    if old is None:
        if not seeding and not record.deleted and record.attendance != -1:
            events.append(DerivedEvent(type="NEW_BOOKING", ...))
        new_states[record.record_id] = _state_from_record(record)
        continue

    # Удаление терминально: записи больше нет, остальное по ней не считаем.
    if record.deleted:
        if not old.deleted:
            events.append(DerivedEvent(type="DELETED", ...))
        new_states[record.record_id] = _state_from_record(record)
        continue

    # Возврат: была удалена или отменена, снова стала активной.
    # Это NEW_BOOKING — как в приложении (SessionChangeDetector:45,71).
    if old.deleted or (old.attendance == -1 and record.attendance != -1):
        events.append(DerivedEvent(type="NEW_BOOKING", ...))
        new_states[record.record_id] = _state_from_record(record)
        continue

    # Отмена тоже обрывает разбор (SessionChangeDetector:61-66).
    if old.attendance != -1 and record.attendance == -1:
        events.append(DerivedEvent(type="CANCELLED", ...))
        new_states[record.record_id] = _state_from_record(record)
        continue

    # Дальше — обычные изменения активной записи, они могут совпасть:
    # перенос и смена статуса за один цикл дают два разных события.
    if old.date != record.date or old.time != record.time:
        events.append(DerivedEvent(type="RESCHEDULED", ..., prev_date=old.date, prev_time=old.time))

    if record.attendance == 2 and old.attendance != 2:
        events.append(DerivedEvent(type="CLIENT_CONFIRMED", ...))

    if record.attendance == 1 and old.attendance != 1:
        events.append(DerivedEvent(type="CLIENT_ARRIVED", ...))

    new_states[record.record_id] = _state_from_record(record)
```

**Что осталось прежним и ломать это нельзя:** правило §6.3 «перенос и смена
статуса за один цикл — два события» продолжает работать, эти две ветки идут без
`continue`. Сидирование (`old is None` при пустом `previous`) не тронуто.

#### Чем проверять

Новые тесты в `tests/test_events.py` — к существующим 14, не вместо них:

| Тест | Ожидание |
|---|---|
| `deleted=1` и `attendance=-1` одновременно | **одно** событие `DELETED`, не два |
| запись уже была `deleted=1`, пришла снова с изменённой датой | ноль событий |
| `deleted` из `1` в `0` | одно `NEW_BOOKING` |
| `attendance` из `-1` в `0` | одно `NEW_BOOKING` |

## 4. Мелочи

Каждая сама по себе некритична, но все три — в одном коммите.

### 4.1 Новый httpx-клиент на каждый пуш

[app/fcm.py:77](../../neiro-push-events/app/fcm.py#L77):
`async with httpx.AsyncClient(timeout=20.0) as client:` внутри
`send_events_push` — то есть новое соединение и новый TLS-handshake на каждое
сообщение каждого устройства.

Для YClients клиент создаётся один раз на процесс и переиспользуется
([yclients.py:29](../../neiro-push-events/app/yclients.py#L29)) — это и есть
образец, план §9.2 требует того же.

**Решение:** завести клиент в `FcmSender.__init__` и метод `aclose()`, а в
[main.py](../../neiro-push-events/app/main.py) закрывать его в `lifespan` рядом
с `yclients_client.aclose()`:

```python
await poll_service.stop()
await yclients_client.aclose()
await fcm_sender.aclose()
```

Для этого `FcmSender` в `lifespan` придётся собрать в отдельную переменную —
сейчас он создаётся прямо в аргументах `PollService(...)`.

### 4.2 `max_pages` обрезает молча

[app/yclients.py:62](../../neiro-push-events/app/yclients.py#L62): `while page
<= max_pages`. Упёрлись в лимит — цикл вышел, вернулось что успело набраться.
Ни лога, ни ошибки, ни признака обрезания.

При лимите 100 страниц по 100 записей это 10 000 записей на компанию за 62 дня
— упереться маловероятно. Но если это случится **во время сидирования**,
состояния засеются частично, и всё, что не влезло, следующим циклом приедет как
`NEW_BOOKING`. Та же лавина, что и в
[stage5-review §2.1](stage5-review.md#21-сидирование-два-источника-правды), но с
другой стороны.

**Решение: не падать, но оставить след.** Падать нельзя — если у компании
действительно столько записей, компания уйдёт в вечный backoff.

```python
else:
    logger.warning(
        "records truncated company=%s: hit max_pages=%s, fetched=%s",
        company_id, max_pages, len(all_records),
    )
```

`else` у `while` выполняется, когда цикл завершился по условию, а не через
`break` — то есть ровно в случае упирания в лимит. Если такая конструкция
кажется неочевидной, написать обычный флаг, но след обязателен.

### 4.3 Два формата времени в БД

`utc_now_iso()` ([database.py:9](../../neiro-push-events/app/database.py#L9))
пишет `2026-07-26T12:00:00+00:00`. А `purge_old_data`
([database.py:474](../../neiro-push-events/app/database.py#L474)) и `stats()`
сравнивают эти строки с `datetime('now', …)`, которая отдаёт
`2026-07-26 12:00:00` — без `T` и без смещения.

Сейчас это **работает случайно**: сравнение строковое, а префикс `YYYY-MM-DD`
сортируется лексикографически правильно, поэтому 30-дневный порог соблюдается.
Расходятся они только когда даты совпадают до дня: там `T` (0x54) больше
пробела (0x20), и запись выглядит на сутки новее.

Для ретеншена в 30 дней погрешность в сутки безразлична. **Ничего не менять** —
но записать комментарий у `utc_now_iso`, чтобы следующий, кто захочет
сравнивать с точностью до часа, не наступил:

```python
def utc_now_iso() -> str:
    """ISO-8601 UTC: `2026-07-26T12:00:00+00:00`.

    Внимание: SQLite-функция datetime('now') отдаёт другой формат —
    `2026-07-26 12:00:00`, без T и без смещения. Строковые сравнения между
    ними верны только на уровне даты (общий префикс YYYY-MM-DD); на точности
    до часа они разъедутся. Ретеншену этого хватает, более тонким сравнениям —
    нет.
    """
```

### 4.4 Курсор не двигается без `last_change_date`

[app/yclients.py:139–144](../../neiro-push-events/app/yclients.py#L139-L144):
`next_changed_after` смотрит только `record.last_change_date`. Старый сервис
([server/app/yclients.py:110](../../server/app/yclients.py#L110)) при пустом
поле откатывался на `record.datetime`.

**Ничего не менять — новое поведение правильнее.** `datetime` это время
**визита**, а не время изменения; подставлять его в курсор изменений — способ
перескочить вперёд и пропустить правки. Docstring функции ссылается на старый
сервис как на образец, и это единственное расхождение — дописать туда одну
строку, чтобы расхождение не выглядело недосмотром:

```python
    Фолбэка на `datetime` (как в старом сервисе) намеренно нет: это время
    визита, а не время изменения — по нему курсор перескочит вперёд.
```

Если `last_change_date` пуст у всех записей пачки, курсор не двигается и
следующий цикл перезапросит то же окно. Лишняя работа, но не потеря.

## 5. Что косяком не является

Чтобы не «чинили» заодно:

**`Database.stats()` не вызывается ниоткуда.** Это не мёртвый код, а задел под
Этап 6: `GET /health` из таблицы [плана §6.2](plan.md) должен отдавать «FCM
настроен, аккаунты, устройства, последний опрос, ошибки, событий за сутки».
Сейчас [main.py:54](../../neiro-push-events/app/main.py#L54) возвращает голое
`{"status": "ok"}` — этого достаточно для приёмки Этапа 1 («`/v2/health`
отвечает публично»), остальное доделывается в Этапе 6. `PollService.fcm_configured`
там же и пригодится. **Не удалять и не расширять сейчас.**

**`connect()` с `try/finally`** ([database.py:166](../../neiro-push-events/app/database.py#L166))
написан правильно: `finally` закрывает соединение при любом исходе, `commit`
только при успешном. Не «упрощать» в ранний `return` — по
[CLAUDE.md](../../CLAUDE.md) такие конструкции стоят намеренно.

**`SecretBox` падает на пустом ключе** ([security.py:20](../../neiro-push-events/app/security.py#L20))
— это правильный fail-fast при старте, а не баг.

**Ретеншен каждые 10 секунд** — известный компромисс, пользователь решил
25.07.2026 оставить как в плане, см.
[stage5-review §5.4](stage5-review.md#5-наблюдения-на-будущее-не-трогать-сейчас).

## 7. С чего начинать

**Эти четыре коммита идут ПЕРЕД шестью коммитами
[stage5-review §7](stage5-review.md#7-с-чего-начинать).**

Почему такой порядок: правка `date` меняет формат данных в `record_states` и
требует их сброса ([§2.1](#21-обязательно-сбросить-record_states-после-этой-правки)).
Сидирование из stage5-review как раз занимается тем, что происходит с пустыми
состояниями. Сделать сначала сидирование, а потом сломать формат состояний —
значит проверять сидирование дважды и на разных данных.

**Коммит 1 — `date`** ([§2](#2-блокер-date-уезжает-со-временем)). Функция
`_extract_date`, вызов в `_parse_record`, пункт про сброс `record_states` в
[progress.md](progress.md). Плюс новый `tests/test_yclients.py`
([§6](#6-тесты-чего-не-хватает)) — целиком, а не только про дату: раз файла нет,
заводим его сразу полным.

Сообщение: `Исправил формат даты в событиях YClients`

**Коммит 2 — дифф** ([§3.3](#33-дифф-не-различает-удаление-отмену-и-возврат)).
Удаление и отмена обрывают разбор записи, возврат записи даёт `NEW_BOOKING`.
Плюс шесть тестов из того же раздела. Проверка: **все 14 существующих тестов
`test_events.py` должны пройти без единой правки** — если какой-то упал, правка
задела то, что работало.

Сообщение: `Исправил разбор удаления и возврата записи в диффе`

**Коммит 3 — FCM** ([§3.1](#31-oauth-токен-обновляется-на-каждую-отправку),
[§3.2](#32-invalid_argument-удаляет-живое-устройство)). Проверка
`credentials.valid` перед refresh, `INVALID_ARGUMENT` убран из признаков
мёртвого токена.

Сообщение: `Убрал лишний refresh токена и удаление живых устройств`

**Коммит 4 — мелочи** ([§4](#4-мелочи)). Переиспользование httpx-клиента в
`FcmSender` + `aclose()` в `lifespan`, лог обрезания по `max_pages`, два
комментария (`utc_now_iso`, `next_changed_after`).

Сообщение: `Переиспользовал HTTP-клиент FCM и добавил лог обрезания`

После этого — переходить к [stage5-review §7](stage5-review.md#7-с-чего-начинать),
коммит 1 «одна транзакция».
