# План доводки

Шесть этапов. Обзор и порядок — [README.md](README.md), здесь только работа.

Этап = законченная порция = один коммит. Этапы независимы друг от друга:
порядок ниже — по убыванию пользы, а не по зависимостям. Взять можно любой.

Легенда: `[ ]` не начато, `[~]` в работе, `[x]` готово.

## Как работать по этому плану

Читать первым делом — здесь всё, что нужно агенту, севшему за работу.
Отдельных указаний в задаче не будет: «работай по плану» означает написанное
ниже.

1. **С чего начать** — со строки «Ближайшее действие» в таблице
   [«Где мы сейчас»](#где-мы-сейчас).
2. **Один этап — один коммит**, сообщение берётся из самого этапа. Несколько
   этапов в один коммит не сваливать.
3. **Не пушить и не создавать PR.** Пуш, PR и слияние в `main` делает
   владелец.
4. **Gradle не запускать** — ни `assembleDebug`, ни тесты. Сборку и проверку
   на устройстве делает владелец.
5. **Статусы отмечать честно.** `[x]` — только тому, что действительно
   проверено; коду, который не собирали, — `[~]` с припиской.
6. **Расходится план с кодом — остановиться и спросить**, не подгонять молча.
7. **Секреты и продакшен.** Этапы 1 и 2 трогают боевой сервер и ключи.
   Агент к ним не приступает сам: он готовит команды и объясняет порядок,
   выполняет владелец.

## Этап 1 — ротация `partner_token`

`partner_token` YClients лежал в каждом APK версий до `0.1.0`. Эти сборки
выкладывались публично, значит ключ публичен: любой, кто его вынул, ходит в
YClients от имени владельца. Менять его было нельзя, пока старые сборки
работали — они бы отвалились. `neiro-push-events` погашен 13.08.2026, держать
ключ больше незачем.

Разбор — [updater/RISKS.md § Секреты в публичном APK](../updater/RISKS.md#секреты-в-публичном-apk).

- [ ] Новый `partner_token` выпущен в кабинете `developer.yclients.com`
- [ ] `YCLIENTS_PARTNER_TOKEN` в `~/neiro-push/.env` на Pi заменён на новый
- [ ] Сервис перезапущен, поллер пошёл
- [ ] Вход с телефона проходит — это и есть проверка ключа
- [ ] Старый токен отозван в кабинете (**после** успешной проверки, не раньше)
- [ ] Закомментированные значения в локальном `local.properties` убраны:
      они больше ни на что не годятся

```bash
# 1. заменить ключ на Pi
ssh roster-b3 'cd ~/neiro-push && cp .env .env.bak-$(date +%Y%m%d) && \
  sed -i "s|^YCLIENTS_PARTNER_TOKEN=.*|YCLIENTS_PARTNER_TOKEN=НОВЫЙ|" .env && \
  docker compose up -d --force-recreate'

# 2. сервис жив и опрашивает
ssh roster-b3 'docker logs --tail 20 neiro-push | grep poll'

# 3. и только теперь — вход с телефона
```

Сеть дома недоступна — `roster-b3` меняется на `roster-pi-remote`, скрипты
проекта делают это сами (`neiro-push/scripts/_ssh.sh`).

**Готово, когда:** в логах `neiro-push` идут успешные опросы с новым ключом,
телефон входит и видит календарь, старый токен в кабинете отозван.

**Откат:** `.env.bak-*` рядом на Pi, вернуть строку и пересоздать контейнер.
Откат перестаёт работать в момент отзыва старого токена — поэтому отзыв
последним пунктом.

**Коммита нет:** в репозитории ничего не меняется.

## Этап 2 — первый живой авто-релиз

Автоматика [`release-on-merge.yml`](../../.github/workflows/release-on-merge.yml)
написана 13.08.2026 и ни разу не срабатывала: проверить её можно только
настоящим слиянием PR. Ломаться там есть чему — запуск `Release` на теге,
права токена, перенос раздела `CHANGELOG`.

Порядок целиком — [updater/RELEASE.md](../updater/RELEASE.md#как-выпустить-версию).

- [ ] Слит любой PR, который трогает код (не только `*.md`)
- [ ] Workflow «Релиз по слиянию PR» отработал зелёным
- [ ] В `main` появился коммит `Поднял версию до X.Y.Z`
- [ ] Тег `vX.Y.Z` на месте, `Release` запустился **сам**
- [ ] Релиз с тремя ассетами, описание — из раздела `CHANGELOG`
- [ ] Телефон нашёл версию и обновился
- [ ] `git pull` локально: в `main` уехал чужой коммит

```bash
gh run watch -R Greem4/neiro          # смотреть оба workflow подряд
gh release view --web -R Greem4/neiro # глазами на описание
```

**Если сломалось на середине.** Самый вероятный отказ — тег поставлен, а
`Release` не запустился. Это чинится руками и не требует нового тега:

```bash
gh workflow run release.yml --ref vX.Y.Z -R Greem4/neiro
```

Отказ хуже — версия поднялась, тег поставлен, а сборка упала. Тогда версия
сгорела: удалять тег и ставить заново можно, **только пока релиз не
опубликован**, иначе нужна следующая версия
([RELEASE.md § Если что-то пошло не так](../updater/RELEASE.md#если-что-то-пошло-не-так)).

**Готово, когда:** от слияния PR до релиза на GitHub не сделано ни одного
ручного действия, и телефон обновился сам.

**Коммита нет:** проверяется то, что уже написано.

## Этап 4 — крайние случаи обновления

Обычное обновление доказано делом: `0.1.3` → `0.1.4` → `0.1.5`. Не проверено,
что приложение внятно себя ведёт, когда что-то идёт не так. Каждый пункт —
отдельная проверка на живом телефоне, кода не пишется.

Полный список и способ проверять, не выпуская релизы, —
[updater/TASKS.md § Этап 11](../updater/TASKS.md#этап-11--проверка-на-устройстве).

- [ ] Отказ в системном диалоге — состояние возвращается в `Available`, а не
      висит «Устанавливаю» навсегда
- [ ] Обрыв сети посреди закачки — внятная ошибка, огрызок файла удалён
- [ ] Подменённая сумма в `SHA256SUMS.txt` — `ChecksumMismatch`, установка не
      начинается
- [ ] APK, подписанный другим ключом, — `SignatureMismatch`, файл удалён
- [ ] Android ниже 12 (эмулятор API 24 подойдёт) — путь с системным диалогом
      работает
- [ ] Сборка, установленная через `adb`, обновляется; debug-сборка молчит
- [ ] `ru.vk.store` как installer — самообновление выключено, показана строка
      про магазин

Проверять нужно сборкой **старее** свежего релиза: приложение сравнивает
`versionCode`. Собрать локально `VERSION=0.0.9`, поставить на телефон — и
настоящий релиз станет для неё обновлением.

Проверка RuStore до появления сборки в магазине делается подменой installer:

```bash
adb install -i ru.vk.store neiro-0.0.9.apk
```

**Готово, когда:** все семь пунктов пройдены и отмечены в
[updater/TASKS.md](../updater/TASKS.md#этап-11--проверка-на-устройстве).

**Коммит:** `Отметил проверку обновления на устройстве`

## Этап 6 — сжать `mapping.txt` в релизе

Ассет `mapping-0.1.5.txt` весит **51 МиБ** при APK в 2,5 МиБ — в двадцать раз
больше того, ради чего релиз делается. На шести релизах это 0,3 ГиБ, и растёт
с каждым выпуском.

Выбросить его нельзя: без `mapping` стектрейс из release-сборки не
разворачивается, а повторить сборку с теми же условиями через месяц не выйдет
([updater/RELEASE.md § Что кладётся в релиз](../updater/RELEASE.md#что-кладётся-в-релиз)).
Зато это текст, и жмётся он в разы.

- [ ] Шаг «Собрать ассеты» в
      [`release.yml`](../../.github/workflows/release.yml) сжимает mapping:
      `gzip -9` вместо простого `cp`
- [ ] В релиз уезжает `mapping-<версия>.txt.gz`
- [ ] `SHA256SUMS.txt` не тронут — он про APK, приложение сверяет только его
- [ ] Таблица ассетов в `RELEASE.md` поправлена
- [ ] В [updater/RISKS.md](../updater/RISKS.md) или в `RELEASE.md` дописано,
      что перед `retrace` файл надо разжать

Приложения это не касается: `ReleaseAssets` выбирает `.apk` и
`SHA256SUMS.txt`, `mapping` оно не читает вовсе — проверено по
[`GithubModels.kt`](../../app/src/main/java/ru/greemlab/neiro/update/GithubModels.kt).
Имя `.txt.gz` не оканчивается на `.apk`, поэтому в запасной выбор APK оно тоже
не попадёт.

Насколько сожмётся — не проверено; у текстового mapping обычно раз в
восемь-десять. Точная цифра будет видна на первом же релизе после правки.

**Готово, когда:** в релизе лежит `mapping-<версия>.txt.gz` заметно меньше
прежнего, `gunzip` разворачивает его в рабочий mapping, а самообновление
телефона на этом релизе проходит как раньше.

**Коммит:** `Сжал mapping в релизных ассетах`

## Что делает владелец, а не агент

| Действие | Почему не агент |
|---|---|
| Ротация `partner_token`, правка `.env` на Pi | Секреты и боевой сервер |
| Слияние PR, пуш тегов | Правило проекта: агент не пушит |
| Съёмка скриншотов | Живой телефон и тестовые данные |
| Проверки на устройстве | Живой телефон |
| Тег `archive/services-v1-v2` | Пуш тега |
| Любая сборка Gradle | Правило проекта |
