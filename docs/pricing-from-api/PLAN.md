# Цены занятий из YClients: разбор API и план реализации

> **Уточнено разбором всей истории — см. [HISTORY-2025-2026.md](HISTORY-2025-2026.md).**
> Этот документ писался по данным за июнь–июль 2026 и считает, что ставки лежат
> в API как `fix`. На самом деле `fix` появился только с 01.06.2026, а до этого
> два с половиной года действовала схема `percent 50 %` от прайса (2500 → 2800 → 3000),
> причём переходы между прайсами перекрываются на ~2,5 месяца.

> раздел 4, «Вариант 1», как самостоятельный первый этап больше не годится —
> одной ставкой историю не пересчитать.

## 1. Задача

Сейчас ставки за занятие вводятся руками в настройках профиля:

- `UserProfile.pricePerSession` — ставка за занятие;
- `UserProfile.pricePerDiagnostics` — за диагностику;
- `UserProfile.pricePerIntensiveChild` — за одного ребёнка в интенсиве.

Нужно уйти от ручного ввода и брать корректные суммы из YClients — так,
чтобы цифры в приложении совпадали со страницей расчёта за день
(`https://yclients.com/salary_daily/520135/?date=...`).

Известные ставки со слов пользователя: 1250 → 1400 (прошлый год), 1500 с августа 2026;
диагностика 2250; интенсив 1400 за ребёнка.

---

## 2. Почему сейчас цифры «неверные»

В `sync/YClientsCalendarSync.kt:239-246` автоподстановка цены берёт **стоимость услуги
для клиента**:

```kotlin
val commonPrice = regularServices.mapNotNull { it.cost }
    .groupBy { it }.maxByOrNull { it.value.size }?.key
updated = updated.copy(pricePerSession = commonPrice)
```

`ServiceData.cost` из `/records` — это то, что платит клиент, а не то, что получает
педагог. Фактические значения в фирме 520135:

| Услуга | service_id | Цена клиента (`cost`) | ЗП педагога |
|---|---|---|---|
| Нейрокоррекция | 17390933 | 3000 | **1400** |
| Нейропсихологическая диагностика и консультация | 17390932 | 4500 | **2250** |
| Интенсив (за ребёнка) | 22795230 | 1750 | **1400** |

То есть автоподстановка писала бы 3000 вместо 1400. Плюс сама автоподстановка
срабатывает только на незаполненном профиле
(`if (currentProfile.name.isNotBlank() && currentProfile.isRegistered) return`),
поэтому на практике ставки почти всегда остаются ручными и устаревают.

**Вывод: `service.cost` как источник ставки использовать нельзя.**

## 3. Что нашлось в API (проверено запросами)

У YClients есть публичный раздел «Расчёт зарплат». Заголовки, которые он требует
(`Accept: application/vnd.yclients.v2+json`, `Authorization: Bearer <partner>, User <user>`),
клиент приложения уже шлёт — см. `data/network/YClientsClient.kt:20,53`.

### 3.1 Эндпоинты

| Эндпоинт | Что даёт | Проверен |
|---|---|---|
| `GET /company/{c}/salary/period/staff/daily/{s}/?date_from&date_to` | **ЗП по каждому дню** периода | 200 |
| `GET /company/{c}/salary/period/staff/{s}/?date_from&date_to` | агрегат за период | 200 |
| `GET /company/{c}/salary/staff/{s}/period/?date_from&date_to` | то же, «свой» вариант (право «Доступ к расчёту ЗП только конкретного сотрудника») | 200 |
| `GET /company/{c}/salary/payroll/staff/{s}/calculation/?date_from&date_to` | список закрытых начислений (месяц → сумма) | 200 |
| `GET /company/{c}/salary/payroll/staff/{s}/calculation/{id}` | **детализация начисления по каждой записи** | 200 |
| `GET /company/{c}/salary/staff/{s}/salary_schemes/` | какая схема ЗП и с какой даты (без ставок) | 200 |
| `GET /company/{c}/salary/calculation/staff/daily/{s}/` | взаиморасчёты (баланс), к ставкам отношения не имеет | 200 |

`{s}` — `staff_id`, он уже хранится в приложении: `TokenStorage.staffId`
(`YClientsRepository.staffId`, детект при логине).

### 3.2 Посуточный расчёт — основной источник

```
GET /api/v1/company/520135/salary/period/staff/daily/3618433/
    ?date_from=2026-07-01&date_to=2026-07-27
```

```json
{"success":true,"data":{"period_calculation_daily":[
  {"date":"2026-07-26","period_calculation":{
     "working_days_count":1,"working_hours_count":8.83,
     "group_services_count":0,"services_count":6,
     "services_sum":"18000","total_sum":"18000","salary":"8400"}}],
  "currency":{"symbol":"₽"}}}
```

`salary` — ровно та сумма, что показывает страница `salary_daily`.

Год одним запросом (`2025-08-01..2026-07-27`) отдаётся за **2.5 с, 92 КБ, 361 день**.
Это дёшево — можно тянуть всю историю разом.

### 3.3 Детализация начисления — источник самих ставок

```
GET /api/v1/company/520135/salary/payroll/staff/3618433/calculation/37456953
```

`salary_items[]`, 112 позиций за июнь. Примеры:

```json
{"date":"2026-06-30","time":"16:00","item_type_slug":"record","record_id":1511357589,
 "client_id":255370970,"cost":"3000","salary_sum":"1400",
 "targets":[{"target_type_slug":"service","target_id":17390933,"title":"Нейрокоррекция",
   "cost":"3000","salary_sum":"1400",
   "salary_calculation":{"type_slug":"fix","value":1400,"description":"1 400 ₽ (+0 ₽ от акций)"}}]}

{"date":"2026-06-30","time":"18:00","item_type_slug":"activity","item_id":45394461,
 "cost":"5250","salary_sum":"4200",
 "targets":[{"title":"Интенсив","cost":"5250","salary_sum":"4200"}]}
```

Сводка ставок, вытащенная из этого начисления:

| item_type | target_id | Название | Схема | Ставка | Записей |
|---|---|---|---|---|---|
| record | 17390933 | Нейрокоррекция | `fix` | **1400** | 115 |
| record | 17390932 | Нейропсих. диагностика и консультация | `fix` | **2250** | 1 |
| activity | — | Интенсив | — | 4200 (3 реб.) / 7000 (5 реб.) → **1400/реб.** | 2 |

Здесь же видно `record_id` — то есть ЗП можно связать с конкретной записью журнала.

### 3.4 Правило начисления (выведено из данных, сверено по 4 дням)

- В ЗП идёт **только `attendance == 1`** («пришёл»). Неявка (`-1`) и ожидание — ноль.
- Ставка типа `fix` — **от цены клиента не зависит**: запись 26.07 16:00 с `cost = 0`
  всё равно дала 1400.
- Интенсив идёт одной позицией `activity`: ставка × число **пришедших** детей.
- Записи без услуг (`services: []`) не считаются вообще.

Сверка журнала и ЗП:

| Дата | В журнале | Пришло | ЗП по API | Разложение |
|---|---|---|---|---|
| 26.07.2026 | 9 нейрокоррекций | 6 | 8400 | 6 × 1400 ✅ |
| 19.06.2026 | 9 нейро + 1 диагностика + 1 без услуги | 8 | 12050 | 7 × 1400 + 2250 ✅ |
| 30.06.2026 | 11 обычных + 6 детей интенсива | 5 + 3 | 11200 | 5 × 1400 + 3 × 1400 ✅ |
| 08.06.2026 | 5 детей интенсива | 5 | 7000 | 5 × 1400 ✅ |

### 3.5 История ставок доступна

Помесячно (`period/staff/daily`, один запрос на год):

| Месяц | Услуг | Групповых | ЗП | Средняя ставка |
|---|---|---|---|---|
| 2025-08 | 100 | 0 | 135 500 | 1355 (переход 1250 → 1400) |
| 2025-09 | 88 | 1 | 122 900 | — |
| 2025-10 | 99 | 1 | 138 000 | — |
| 2025-11 | 107 | 1 | 149 800 | — |
| 2025-12 | 86 | 1 | 120 400 | — |
| 2026-01 | 73 | 0 | 102 200 | **1400** |
| 2026-02 | 93 | 0 | 136 600 | 1469 (есть диагностики) |
| 2026-03 | 115 | 0 | 170 600 | 1483 |
| 2026-04 | 115 | 0 | 171 900 | 1495 |
| 2026-05 | 128 | 0 | 193 500 | 1512 |
| 2026-06 | 116 | 2 | 174 450 | — |
| 2026-07 (1–27) | 102 | 0 | 142 800 | **1400** |

Май 2025 — ровно **1250** каждый день. То есть API помнит старую ставку,
и историю за 2025 год можно посчитать корректно, а не по сегодняшней цифре.

### 3.6 Ограничения (важно для дизайна)

1. **Будущее не считается.** `date_to` больше сегодняшней даты → `HTTP 422`,
   `«Расчет заработной платы возможен только по текущую дату»`.
   Диапазон, залезающий в будущее, тоже целиком отбивается.
   → Прогноз по будущим записям всё равно придётся считать самим.
2. **Детализация по записям есть только у закрытых месяцев.** Начисление создаётся
   в конце месяца (июнь → `id=37456953`, создано 30.06 19:14). За июль
   `payroll/.../calculation/` вернул пустой список. Для текущего месяца доступен
   только посуточный агрегат.
3. **Права.** Посуточный эндпоинт документирован как «владельческий»
   (`/salary/period/staff/daily/{s}/`), «своего» посуточного варианта нет.
   На проверяемом аккаунте он отдаёт 200, но у другого сотрудника может быть 403 —
   нужен фолбэк.
4. Ставка меняется **задним числом только по факту**: ставка 1500 с августа появится
   в API лишь после первого отработанного дня августа.

## 4. Варианты реализации

### Вариант 1 — «Автоподстановка ставок» (минимальный)

Оставляем всю арифметику приложения как есть, меняем только источник трёх чисел
в профиле: вместо `service.cost` — ставки из модуля ЗП.

Как добываем:
- основной путь — последнее закрытое начисление
  (`salary_items[].targets[].salary_calculation.value`, сгруппировать по `target_id`
  и по `item_type_slug == "activity"` для интенсива);
- если начисления ещё нет — калибровка по дням текущего месяца: берём день, где
  `group_services_count == 0` и все записи одного вида, ставка = `salary / services_count`.

Обновление — при обычной автосинхронизации, не чаще раза в сутки.

- Плюсы: мало кода, ничего не ломает, ручное переопределение сохраняется.
- Минусы: одна ставка на всю историю — 2025 год всё равно посчитается по 1400/1500;
  не ловит бонусы, штрафы, гарантированный минимум; ставка августа появится с
  задержкой.

### Вариант 2 — «Факт из API + прогноз по ставкам» (рекомендуемый)

Разделяем то, что сейчас смешано в одну формулу:

- **Факт** — прошлые дни и сегодня. Берём `salary/period/staff/daily`, кладём в кэш
  `дата → сумма`. Месяц, год и дашборд по прошлому считаются ровно как в YClients,
  включая ставку 1250 в 2025 году.
- **Прогноз** — будущие дни и незакрытые слоты. Считаем локально по карте ставок
  из Варианта 1.

Новые сущности:
- `data/network/SalaryModels.kt` + методы в `YClientsApi`;
- `domain/models/SalaryRates.kt` — ставки (занятие / диагностика / ребёнок интенсива)
  + дата актуальности;
- `data/SalaryDailyCache.kt` (DataStore) — `дата → сумма` + отметка обновления;
- `sync/SalaryRepository.kt` — обновление кэша.

Политика обновления: текущий месяц — при каждом синке (1 запрос);
прошлые месяцы — один раз, они не меняются после закрытия начисления;
догрузка года — при первом открытии статистики за этот год.

- Плюсы: цифры сходятся с `salary_daily` один в один; история корректна;
  смена ставки не требует ручных действий; бонусы/штрафы учитываются автоматически,
  потому что уже сидят в `salary`.
- Минусы: заметно больше кода; нужен фолбэк на 403 и офлайн; в UI надо честно
  разделить «факт» и «прогноз».

### Вариант 3 — «Полная детализация по записям»

Тянем `salary_items` из закрытых начислений и раскладываем ЗП **по каждой записи**
календаря через `record_id`. Тогда точна и статистика по ученикам.

- Плюсы: максимальная точность, честная разбивка по ученикам и услугам.
- Минусы: работает только для закрытых месяцев (текущий всё равно по Варианту 2);
  требует расширить формат хранения записи
  (`name|status|time|phone|comment` → плюс `record_id` и сумма) — это `SessionParser`,
  `SessionFormat`, миграция данных и весь sync. Дорого и рискованно.

### Рекомендация

**Вариант 2 как цель, Вариант 1 как первый этап и одновременно фолбэк.**
Вариант 3 — отдельной задачей позже, если понадобится разбивка по ученикам.

## 5. Этапы (Вариант 2)

Один этап = один коммит.

1. **API-слой.** Модели ответов + методы в `YClientsApi` / `YClientsRepository`:
   посуточный расчёт, агрегат за период, список начислений, детализация начисления.
   Заголовки уже правильные, менять `YClientsClient` не нужно.
2. **Карта ставок.** `SalaryRates` + вывод ставок из детализации начисления,
   фолбэк-калибровка по дневным агрегатам. Заменить эвристику по `service.cost`
   в `YClientsCalendarSync.autoFillProfile`.
3. **Кэш посуточной ЗП.** `SalaryDailyCache` + `SalaryRepository`, обновление
   из `YClientsCalendarSync` / автосинка, аккуратный фолбэк при 403/422/офлайне.
4. **Подключение к расчётам.** `computeMonthStats`, `computeProfileYearStats`,
   `computeDaySummaryStats`, `computeProfileTotals`: прошлое — из кэша,
   будущее — по ставкам.
5. **UI.** В настройках цены становятся «авто (из YClients)» с возможностью ручного
   переопределения; на сумме дня — пометка, что это расчёт YClients, а не прогноз.
6. **Тесты.** Юнит на разбор ставок, на выбор «факт/прогноз» по дате, на фолбэк
   при недоступном salary API.

## 6. Риски и что нужно решить

| Вопрос | Почему важно |
|---|---|
| **403 на посуточном эндпоинте у других аккаунтов** | «Своего» посуточного варианта в API нет. Нужен фолбэк: агрегат за период + локальный прогноз по ставкам. |
| **Ставка 1500 с августа** | В API она появится только после первого отработанного дня августа. Нужно ли поле «ставка с даты» вручную, чтобы прогноз на август был верным заранее? |
| **Ручные интенсивы** | Интенсивы, заведённые в приложении и отсутствующие в YClients, в `salary` не попадут. Их суммы должны остаться локальными и складываться с фактом. |
| **Налог и выплаты на карту** | `monthlyTaxAmount`, `salaryAdvanceOnCard`, `salaryMainOnCard` YClients не знает — остаются ручными. |
| **Расхождение факта и прогноза** | Пока день не закрыт, сумма может меняться (клиент пришёл/не пришёл). Кэш текущего месяца надо перечитывать при каждом синке. |
| **Лимиты API** | 200 запросов/мин, 5/с. Наша нагрузка: 1 запрос на месяц, год одним запросом. Запас огромный. |

## 7. Приложение: как воспроизвести разбор

Скрипты разведки лежали во временной папке сессии и в репозиторий не попали.
Минимальный воспроизводимый запрос:

```bash
# user_token
curl -s -X POST https://api.yclients.com/api/v1/auth \
  -H 'Accept: application/vnd.yclients.v2+json' \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $YCLIENTS_PARTNER_TOKEN" \
  -d '{"login":"'"$DEV_LOGIN"'","password":"'"$DEV_PASSWORD"'"}'

# ЗП по дням
curl -s "https://api.yclients.com/api/v1/company/520135/salary/period/staff/daily/3618433/?date_from=2026-07-01&date_to=2026-07-27" \
  -H 'Accept: application/vnd.yclients.v2+json' \
  -H "Authorization: Bearer $YCLIENTS_PARTNER_TOKEN, User $USER_TOKEN"
```

Секреты — из `local.properties` (`YCLIENTS_PARTNER_TOKEN`, `DEV_LOGIN`, `DEV_PASSWORD`).
