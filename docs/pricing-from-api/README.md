# Цены занятий из YClients — краткое содержание

Подробности: [PLAN.md](PLAN.md)

## Главное

1. **Текущая автоподстановка цены неверна по определению.** Она берёт
   `service.cost` — это цена для клиента (3000 ₽), а не ЗП педагога (1400 ₽).
2. **В YClients есть публичный API расчёта зарплат**, и он отдаёт ровно те суммы,
   что показывает страница `salary_daily`. Проверено на боевой фирме 520135.
3. **Ставки достаются точно, а не угадываются**: в детализации начисления лежит
   `salary_calculation: {type_slug: "fix", value: 1400}` по каждой услуге.
4. **История ставок в API есть** — май 2025 отдаётся по 1250 ₽, 2026 год по 1400 ₽.
   Значит статистику за прошлые годы можно посчитать корректно.
5. **Будущее API не считает** (HTTP 422), поэтому прогноз по будущим записям
   всё равно остаётся на стороне приложения.

## Ставки в фирме 520135 (июнь 2026)

| Услуга | Цена клиента | ЗП педагога |
|---|---|---|
| Нейрокоррекция | 3000 | **1400** (fix) |
| Нейропсихологическая диагностика | 4500 | **2250** (fix) |
| Интенсив, за ребёнка | 1750 | **1400** |

Правило: в ЗП идёт только статус «пришёл»; ставка фиксированная и от цены клиента
не зависит; интенсив = ставка × число пришедших детей.

## Три варианта

| Вариант | Суть | Оценка |
|---|---|---|
| 1. Автоподстановка ставок | Меняем только источник трёх чисел в профиле | Дёшево, но история за 2025 останется неверной |
| 2. **Факт из API + прогноз по ставкам** | Прошлые дни — реальная ЗП из API, будущие — расчёт по ставкам | **Рекомендуется** |
| 3. Детализация по каждой записи | ЗП кладём в каждую запись через `record_id` | Точнее всех, но ломает формат хранения записей |

Предлагаемый ход: Вариант 2 как цель, Вариант 1 как первый этап и фолбэк.

## Что нужно решить до реализации

- Нужно ли ручное поле «ставка с даты»? Ставка 1500 с августа появится в API
  только после первого отработанного дня августа.
- Как вести себя, если у аккаунта нет прав на посуточный расчёт (403).
- Ручные интенсивы и налог остаются локальными — YClients про них не знает.
