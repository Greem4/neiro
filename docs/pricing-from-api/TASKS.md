# Задачи: перевести расчёт денег на честную модель

Что делать в коде после разбора [HISTORY-2025-2026.md](HISTORY-2025-2026.md).
Один этап = одна законченная порция = один коммит.

Порядок не случайный: этапы 1–3 не трогают сеть и UI (чистая логика + тесты),
этап 4 включает поправку и уже меняет цифры на экране, этапы 5–7 добавляют
факт из API. **После каждого этапа приложение должно собираться и работать.**

---

## Что не так с кодом сегодня

Три отдельные проблемы, их важно не смешивать:

1. **Одна ставка на всю историю.** `UserProfile.pricePerSession: Double` —
   одно число, применяемое ко всем годам. История требует минимум трёх ставок
   с датами. Любой отчёт за 2025 год сейчас неверен.
2. **Четыре голых `Double` протащены через всю иерархию.** `pricePerSession`,
   `pricePerDiagnostics`, `pricePerIntensiveChild`, `monthlyTaxAmount` руками
   передаются в `computeMonthStats`, `computeProfileYearStats`,
   `computeDaySummaryStats`, `computeProfileTotals` и дальше в composable —
   `CalendarScreen.kt` (7 мест), `CalendarDialogs.kt`, `DayDetailsDialog.kt`.
   Добавить пятый параметр — значит снова тронуть десяток файлов.
   Нужен один объект-носитель ставок.
3. **Автоподстановка цены берёт не то поле.** `YClientsCalendarSync.kt:239-246`
   читает `ServiceData.cost`, который равен `0` у трети записей (абонемент).
   Нужное поле `first_cost` в модели `ServiceData` отсутствует.

## Этап 1. Модель ставок с историей

**Цель:** одно место, которое отвечает на вопрос «какая ставка была в эту дату».
Чистая логика, ни сети, ни UI.

Новый файл `domain/models/SalaryRates.kt`:

```kotlin
/** Ставка за занятие, действующая с даты [from] включительно. */
data class SessionRate(val from: LocalDate, val amount: Double)

@Immutable
data class SalaryRates(
    val sessionRates: List<SessionRate> = DEFAULT_SESSION_RATES,
    val perDiagnostics: Double = 2250.0,
    val perIntensiveChild: Double = 1400.0,
    val monthlyTax: Double = 6500.0,
) {
    fun sessionRateAt(date: LocalDate): Double = ...
}
```

Дефолт (согласовано 27.07.2026):

| С даты | Ставка |
|---|---|
| 01.01.2025 | 1250 |
| 01.08.2025 | 1400 |
| 01.08.2026 | 1500 |

Требования:

- `sessionRates` хранится **отсортированным по `from`**, ищем последний период,
  у которого `from <= date`.
- Дата раньше первого периода → берём первую ставку (не ноль и не исключение:
  занятие из 2024 года не должно обнулять статистику).
- Пустой список → `0.0`, как сейчас при незаполненном профиле.
- Интенсивы до 2026 года не считаем — либо отдельным полем
  `intensivesFrom: LocalDate = 2026-01-01`, либо периодами как у занятий.
  **Решить в начале этапа, а не по ходу.**

Тесты `SalaryRatesTest`: граница периода (31.07 → 1250, 01.08 → 1400),
дата до начала, пустой список, несортированный вход.

## Этап 2. Поправка «YClients врёт»

**Цель:** отдельная от ставок сущность — периоды, где данным YClients верить нельзя.

Февраль–май 2026 нужно считать по 1400, хотя API отдаёт 1500.
**Не зашивать диапазон в код**: если центр пересчитает эти месяцы задним числом,
жёсткая поправка начнёт врать в другую сторону.

```kotlin
/** Период, за который берём расчёт по ставке, а не факт из YClients. */
data class SalaryOverride(
    val from: LocalDate,
    val to: LocalDate,
    val reason: String,   // "В YClients схема 50 % не закрыта, начисляется 1500 вместо 1400"
)
```

Дефолт — один период: `2026-02-01 .. 2026-05-31`.

Тесты: дата внутри/на границах/вне периода, пересекающиеся периоды,
пустой список.

## Этап 3. Носитель ставок вместо четырёх Double

**Цель:** убрать протаскивание четырёх параметров, подготовить место для факта из API.

- Ввести `EarningsContext` (или расширить `SalaryRates`) — один объект,
  который получают все четыре калькулятора вместо `pricePerSession`,
  `pricePerDiagnostics`, `pricePerIntensiveChild`, `monthlyTaxAmount`.
- Переписать сигнатуры: `computeMonthStats`, `computeProfileYearStats`,
  `computeDaySummaryStats`, `computeProfileTotals` и их `remember*`-обёртки.
- Обновить вызовы: `CalendarScreen.kt`, `CalendarDialogs.kt`,
  `DayDetailsDialog.kt`, `ProfileContent.kt`, `ProfileYearStatsSection.kt`.
- Внутри калькуляторов заменить `pricePerSession` на `rates.sessionRateAt(date)` —
  дата уже есть в каждом цикле (`for ((date, sessions) in dayData)`).

Осторожно: в `computeMonthStats` ставка используется дважды — в `grossEarned`
и в `statsByStudent`. Обе должны стать по-дневными, иначе статистика по ученикам
разъедется с суммой месяца.

**Ничего не должно поменяться в цифрах**, если задать одну ставку с 01.01.2025.
Это проверка, что рефакторинг чистый: существующие тесты
(`CalendarStatsCalculatorTest`, `ProfileYearStatsTest`, `DaySummaryStatsTest`,
`ProfitDisplaySettingsTest`) должны пройти после механической правки конструкторов.

## Этап 4. Хранение и редактирование ставок

**Цель:** ставки живут в профиле и правятся руками.

- `UserProfile`: добавить `salaryRates: SalaryRates`, `overrides: List<SalaryOverride>`.
- `UserProfileJson`: миграция. Старый профиль с `pricePerSession = 1400` должен
  превратиться в **дефолтную лестницу**, а не в одну ставку 1400 с начала времён —
  иначе 2025 год останется неверным у всех, кто уже пользуется приложением.
  Старые поля не удалять сразу: `normalizeLegacy` уже работает по
  `pricePerSession > 0.0`, сломать её нельзя.
- `SettingsScreen.kt`: редактор списка «с даты — ставка», добавить/удалить/изменить.
  Диагностика, интенсив и налог остаются как есть.
- Тесты в `UserProfileJsonTest`: старый JSON без `salaryRates`, новый JSON,
  битый JSON (не должен ронять — сейчас возвращается пустой профиль).

После этого этапа отчёты за 2025 уже верные, **ещё без единого сетевого запроса**.
Контрольные значения — таблица раздела 3 в отчёте.

## Этап 5. API-слой зарплат

**Цель:** уметь спросить у YClients, сколько начислено. Пока без применения.

- `data/network/SalaryModels.kt` — модели ответов.
- `YClientsApi`: три метода
  - `GET company/{c}/salary/period/staff/daily/{s}/` — ЗП по дням;
  - `GET company/{c}/salary/payroll/staff/{s}/calculation/` — список начислений;
  - `GET company/{c}/salary/payroll/staff/{s}/calculation/{id}` — детализация.
- `YClientsRepository`: обёртки, возвращающие `ApiResult`.
  Заголовки уже правильные, `YClientsClient` не трогать.

Обработать явно, а не «упало — и ладно»:

| Код | Что значит | Поведение |
|---|---|---|
| 422 | диапазон залезает в будущее **или** больше года | не ошибка: обрезать период и повторить |
| 403 | нет прав на посуточный расчёт | тихий фолбэк на расчёт по ставкам |
| 401 | протух `user_token` | уже есть общий logout-механизм, не дублировать |

Формат и примеры ответов — [API-HOWTO.md](API-HOWTO.md), раздел 5.

## Этап 6. Кэш факта

**Цель:** `дата → начисленная сумма`, чтобы не дёргать сеть на каждый пересчёт.

- `data/SalaryDailyCache.kt` — DataStore, по образцу `CalendarDataStore`
  (там уже есть `corruptionHandler`, повторить — битый кэш не должен ронять старт).
- `sync/SalaryRepository.kt` — обновление кэша.
- Политика: текущий месяц — при каждом синке (1 запрос); прошлые месяцы —
  один раз после закрытия начисления; год — при первом открытии статистики за него.
- Встроить в `YClientsCalendarSync` / `AutoSyncCoordinator`.

**Не трогать live-опрос и push** — это работающие подсистемы, к деньгам
отношения не имеют.

## Этап 7. Выбор источника: факт или ставка

**Цель:** правило, по которому считается каждый месяц. Ядро всей задачи.

```
дата в периоде override  → считаем по ставке (YClients врёт)
дата в прошлом, факт есть → берём факт из кэша
дата в прошлом, факта нет → считаем по ставке (офлайн, 403, не догрузили)
дата в будущем            → считаем по ставке (API будущее не отдаёт)
```

- Провести источник через калькуляторы (объект из этапа 3 уже готов).
- Расхождение факта и расчёта по ставке в месяце **без** override — не прятать.
  Это сигнал, что в YClients опять поменяли схему; ровно так и обнаружилась
  история с 1500.

Тесты: месяц целиком из факта, месяц под override, месяц наполовину в будущем,
месяц без данных, факт есть но нулевой (не путать с «факта нет»).

## Этап 8. UI: развести факт, расчёт и прогноз

- На сумме дня и месяца — пометка, откуда цифра: «из YClients» / «по ставке».
- В настройках — редактор поправок с текстом причины.

Пометки должны подчиняться существующим настройкам отображения прибыли
(`ProfitDisplaySettings`, `display.showPricePerSession`) — не показывать деньги
там, где пользователь их выключил.

## Чего в этой задаче нет

Чтобы не расползлось:

- **Интенсивы 2025** — не считаем вообще, решено.
- **Разбивка ЗП по каждой записи** через `record_id` (Вариант 3 в [PLAN.md](PLAN.md)) —
  требует менять формат хранения записи и весь sync. Отдельной задачей, если
  понадобится статистика «сколько принёс каждый ребёнок».
- **Налог и выплаты на карту** — YClients про них не знает, остаются ручными.
- **Push, live-опрос, уведомления, архив** — не трогать.

   или пересчёт по текущей ставке? Решено считать по факту, но в UI это
   может выглядеть как «доход упал», хотя выросла ставка.
4. **Август 2026: проверить, как оформили 1500** — `fix` или снова процент.
   До первого отработанного дня августа этого не видно.
