# Фундамент модели цен — решения 28.07.2026

Как устроены деньги в приложении. Документ уточняет [TASKS.md](TASKS.md):
часть этапов оттуда отпадает или меняется, сводка — раздел 9.

Исходная точка: приложение — личный инструмент одного специалиста, но им
должны начать пользоваться другие специалисты центра. Доступа к их данным
сейчас нет. Значит задача не «сделать продукт для центра», а **не закрыть
себе дорогу к нему**, оставаясь личным инструментом.

---

## 1. Три принципа

Всё остальное — следствия. При спорах о деталях сверяться с этими тремя.

### 1.1. Ручной ввод — источник правды, API — источник наблюдений

То, что человек ввёл сам, важнее того, что отдаёт YClients. Февраль–май 2026 —
готовый пример: API четыре месяца отдавал 1500 ₽ за занятие, правдой было 1400.

Приложение никогда не переписывает введённое человеком. Оно может только
**сообщить**, что видит другое.

### 1.2. Верно по умолчанию, без действий пользователя

Кто-то полезет в статистику и всё поправит, а кто-то забьёт. Правильная цифра
не должна зависеть от того, потрогал ли её пользователь: приложение выставляет
всё как надо само, в момент закачки данных.

Любой мастер, любое окно — способ **подтвердить и поправить**, а не условие
получения верных цифр.

### 1.3. Профиль — про сейчас, история — про прошлое

| Зона времени | Кто главный | Меняется ли |
|---|---|---|
| Прошлые месяцы | замороженная запись месяца | только вручную, по клику в статистике |
| Текущий месяц | **цена в профиле** | да, пересчитывается на лету |
| Будущие месяцы | **цена в профиле** | да |

Цена, стоящая в профиле, действует на текущий месяц и все последующие.
Прошлое она не задевает: у каждого закрытого месяца своя цена внутри него.

## 2. Три величины вместо одной ставки

Главная ошибка сегодняшней модели: `UserProfile.pricePerSession` — одно число.
На деле независимых величин три, и хранить надо все.

| Величина | Пример | Откуда | Кто меняет |
|---|---|---|---|
| **Прайс клиента** | 2500 → 2800 → 3000 | `first_cost` в записи | центр |
| **Правило начисления** | `percent 50` / `fix 1400` | `targets[].salary_calculation` | центр |
| **Факт начисления** | 1250 → 1400 → 1500 | `salary` в посуточном расчёте | следствие первых двух |

Зачем разделять — на живом примере. При переходе прайса 2800 → 3000
специалисту оставили 1400: правило перестало быть `percent 50` и фактически
стало `fix 1400` (46,7 %), **вся прибавка в 200 ₽ ушла центру**. В YClients
правило не поправили, и четыре месяца начислялось 1500 вместо 1400.

Если модель хранит только ставку — это «необъяснимая ошибка», которую
приходится зашивать в код. Если хранит прайс и правило отдельно — это
**штатное расхождение: договорённость против настройки**, и приложение
показывает его само. У другого специалиста такое же расхождение всплывёт
автоматически, без ручного разбора.

Практическое следствие: **никаких хардкодов «февраль–май 2026» в коде.**

## 3. История месяцев вместо лестницы ставок

Прошлое **не пересчитывается**. У каждого прошедшего месяца есть собственная
запись с ценой и суммой, и живёт она вечно, пока человек её не поправит.

Отсюда важное упрощение: **таблица «ставка с даты» не нужна.** Она нужна была
только чтобы восстанавливать прошлое расчётом. Восстанавливать нечего —
прошлое хранится готовым. Профиль отвечает за «сейчас и вперёд» (принцип 1.3),
а история за прошлое.

Это снимает и проблему из README п.4: переходы между прайсами размазаны по
клиентам (абонементы по старой цене живут ~2,5 месяца), и никакое правило
«ставка X с даты Y» историю не восстанавливает. Хранимой записи месяца это
безразлично.

### 3.1. Что лежит в записи месяца

```
staffId: Long              // см. 8.1
month: YearMonth

sessions: Int              // занятий — из локального календаря
pricePerSession: Double    // цена за занятие в этом месяце
priceDiagnostics: Double
priceIntensiveChild: Double
tax: Double

factGross: Double?         // что говорит YClients — для сверки
origin: AUTO | MANUAL      // кто выставил цену (см. 6.1)
frozen: Boolean            // месяц закрыт, не пересчитывается
resolved: Boolean          // расхождение разобрано, больше не спрашивать
note: String               // «В YClients percent 50, по договорённости fix 1400»
```

Сумма месяца — не хранимое число, а результат: `sessions × pricePerSession`
плюс диагностики и интенсивы. Поэтому правится **цена за занятие**, а сумма
пересчитывается сама. Так и работает редактор в статистике (раздел 5).

### 3.2. Откуда берётся цена месяца

Приоритет — по принципам 1.1 и 1.3:

| Условие | Цена месяца |
|---|---|
| Человек поправил (`origin = MANUAL`) | его значение, навсегда |
| Есть факт из YClients | `factGross ÷ sessions` — «цена, которую придумало приложение» |
| Факта нет (офлайн, 403, не догрузили) | цена из профиля на тот момент |
| Месяц текущий или будущий | цена из профиля, живьём |

Деление `factGross ÷ sessions` считается после вычета диагностик и интенсивов —
у них своя цена:

```
цена занятия = (factGross − диагностики×цена − интенсивы×цена) ÷ (sessions − диагностик)
```

Важно: в посуточном расчёте диагностики **не отделены** — `services_count`
считает занятия и диагностики вместе, отдельным счётчиком идут только группы
(`group_services_count`).

Проверено на 19.06.2026 (7 занятий + диагностика в 17:55, две неявки не в счёт):

```
services_count = 8       ← диагностика посчитана как обычная услуга
services_sum   = 25500   = 7×3000 + 4500
salary         = 12050   = 7×1400 + 2250

наивно:      12050 ÷ 8        = 1506 ₽   ← неверно
с вычетом:  (12050 − 2250) ÷ 7 = 1400 ₽   ← верно
```

**Диагностики определяем так же, как сейчас** — по подстроке «диагностика»
в названии услуги (`YClientsCalendarSync.kt:721-723`), ничего не меняя.
Цену для вычета берём **из самой локальной записи**: она хранится в строке
дня (`__DIAGNOSTICS__:2250|имя|статус|время`), а не в профиле — в старых
записях там лежит цена, актуальная на момент синхронизации.

Если локальных записей за месяц нет, диагностика растворится в занятиях
и слегка завысит цену; за всю историю их три штуки, влияние копеечное.

**Откуда `sessions`:** за прошлые месяцы — число из посуточного расчёта
(`services_count`), то есть делим на то же, из чего считался факт. За текущий
месяц — локальный календарь, как и весь текущий расчёт. Обычно числа совпадают
и разницы нет.

Если не совпали (в YClients 80, в календаре 78) — **цена считается по числу из
API** (иначе она завысится), а на экране остаётся локальное число плюс строка
«в YClients 80». Расхождение не прячем: обычно это удалённая или недошедшая
до календаря запись, и человеку полезно об этом знать.

**Налог за прошлые месяцы** при первой заливке истории проставляется текущий
из профиля во все месяцы (6500 ₽ был всегда). Если когда-то было иначе —
правится помесячно.

### 3.3. Месяцы, которых нет в календаре

Человек ставит приложение в июле 2026 — локальных записей за 2025 нет,
а в YClients данные есть. Такие месяцы **показываются в статистике цифрами
из API**: сумма и число занятий из посуточного расчёта, календарь при этом
остаётся пустым.

Ради этого история и заводится: иначе прошлое теряется при каждой установке.

Следствие для кода: `availableStatsYears` (`ProfileYearStats.kt:66`) сейчас
собирает годы только из `dayData` — годы из истории месяцев надо добавить,
иначе 2025-й просто не появится в переключателе.

### 3.4. День из прошлого — тоже из API

Открытый день из марта 2025 показывает **сумму этого дня из посуточного
расчёта**, а не «цена месяца × занятия». Раз факт по API подтверждён верным,
день должен показывать именно его.

Поэтому факт хранится по дням (а не одной суммой за месяц): `дата → salary`.
Заморозка при этом остаётся помесячной.

Порядок для `computeDaySummaryStats`:

```
есть факт за этот день  → показываем его
факта нет, месяц закрыт → цена месяца × занятия дня
день текущий/будущий    → цена профиля × занятия дня
```

Что нельзя: брать цену из профиля для прошедшего дня — тогда день из марта
2025 посчитается по сегодняшней цене и не сойдётся с месяцем в статистике.

### 3.5. Чем за это платим

Если истории в API нет (403 у сотрудника без прав владельца, офлайн при
установке), прошлые месяцы посчитаются по текущей цене профиля: 2025 год
покажет 1400 вместо 1250. Правится вручную по месяцам в статистике.

Это принято осознанно: прошлая статистика не критична, а альтернатива —
возвращать лестницу ставок ради случая, который у большинства не наступит.

## 4. Закрытие месяца: сверка и мини-окно

Месяц закончился → приложение сравнивает **свою** цену (ту, что стояла в
профиле) с фактом YClients. Дальше два пути.

### Совпало — замораживаем молча

`frozen = true`, никаких окон. Месяц уехал в историю, больше не пересчитывается
и не дёргает сеть.

### Не совпало — замораживаем по цене приложения и ждём

Решено: окно **не всплывает само** — ни при открытии приложения, ни поверх
работы. Оно тихо ждёт в статистике, пока человек до него дойдёт.

Значит заморозка решения не ждёт, иначе месяц висел бы живым и дёргал сеть:

- месяц замораживается **по цене приложения** — той, что стояла в профиле
  и которую человек видел весь месяц;
- `resolved = false`, в статистике появляется отметка о расхождении;
- разбор — когда человек откроет этот месяц.

Выбор «цена приложения по умолчанию» — из принципа 1.1: до тех пор пока
человек не сказал иначе, правда — то, что настроено у него, а не то, что
насчитал YClients.

### Разбор — по клику в статистике

Открывается из сводки месяца (раздел 5), не сам:

```
Июль 2026 — расхождение

  Приложение считало   1400 ₽ × 80 занятий  =  112 000 ₽
  YClients начислил    1500 ₽ × 80 занятий  =  120 000 ₽
                                    разница     8 000 ₽

  Что отправляем в историю?

  ( ) 1400 ₽ — как считало приложение     ← сейчас так
  ( ) 1500 ₽ — как в YClients
  ( ) Другая цена: [____]

                              [ В историю ]
```

После выбора `resolved = true`, вопрос закрыт навсегда.

**`resolved` — отдельный флаг, а не следствие правки.** Если человек выбрал
«как считало приложение», цена не меняется, и без флага та же отметка висела
бы вечно. Разобранный месяц молчит.

### Текущий месяц: сообщаем сразу

Ждать закрытия месяца, чтобы сказать о расхождении, не надо. Как только факт
за уже прошедшие дни расходится с ценой профиля — мягкая строка в статистике,
без окон и без push.

Смысл — ранний сигнал: историю с 1500 так можно было заметить в феврале, а не
в июне. Пугать этим никого не придётся: специалист свою цену занятия знает,
и расхождение для него не новость, а информация.

### Условие заморозки

```
месяц не текущий
  И факт за месяц получен
  И прошло ≥ 7 дней с конца месяца
→ сверка → заморозка (с окном или без)
```

Семь дней — запас на удаления задним числом
(`salary_discrepancy: {reason: "deleted"}`, GAPS п.7). Не 1-го числа.

Заморозка **обратима** и ничего не удаляет: она лишь говорит «не пересчитывай».
Разморозка — в статистике, на выбранном месяце.

Отложено: в API, возможно, есть точный признак закрытия начисления
(`salary/payroll/staff/{s}/calculation/` — появляется ли там текущий, ещё не
закрытый месяц). Не проверялось. Если признак есть — заменит эвристику по дням.

## 5. Редактор — в статистике, на графике по месяцам

Отдельного экрана нет. Правка живёт там, где человек и так смотрит цифры.

**Поток:** статистика → клик по месяцу на графике → сводка внизу (месяц,
занятий, сумма, при необходимости пометка «может быть неверно») → клик по
сводке → раскрываются данные месяца и цена за занятие → правишь цену →
вопрос закрыт.

### Что уже есть в коде

`ui/profile/ProfileYearStatsSection.kt`:

| Что нужно | Состояние |
|---|---|
| Клик по месяцу на графике | **есть**, 12 кликабельных зон, строки 542–554 |
| Выбранный месяц | **есть**, `selectedMonthIndex`, строка 345 |
| Сводка под графиком | **есть**, `SelectedMonthSummary`, строки 585–593: месяц, занятий, сумма |

### Что достроить

- **Дисклеймер на всех месяцах с автоматической ценой.** Решено: не выборочно,
  а на каждом месяце, где цену поставило приложение (`origin = AUTO`) —
  она везде может быть неверной, и честнее сказать это прямо. Формулировка
  спокойная, не как ошибка: «цена рассчитана автоматически, проверьте».
  Снимается, как только человек подтвердил или поправил месяц
  (`origin = MANUAL`).
- **Отдельная отметка о расхождении** — заметнее дисклеймера, только на
  месяцах с `resolved = false`. Видна, не открывая месяц: маркер на столбце
  графика и строка в свёрнутой сводке. Стоит показать и в заголовке секции
  «Статистика», чтобы человек знал, что там что-то ждёт, не разворачивая её.
- **Раскрытие по клику**: цена за занятие, откуда она (`из YClients` /
  `по вашей цене` / `вы поправили`), диагностики, интенсивы, налог,
  пометка «закрыт», и — если есть расхождение — кнопка разбора (раздел 4).
- **Правка цены за занятие** прямо здесь — и **только её**. Сумма
  пересчитывается сама (раздел 3.1). Запись: `pricePerSession`,
  `origin = MANUAL`, `resolved = true`.
  Диагностика, интенсив и налог в месяце берутся из профиля и здесь не
  правятся: меняются они редко и весят мало, а три поля вместо одного
  превращают сводку в форму. Поля в записи месяца при этом есть (3.1) —
  если понадобится, редактор дописывается без миграции данных.
- **Разморозка** — там же, рядом с пометкой «закрыт».

### Ограничения

- Всё подчиняется `ProfitDisplaySettings`
  (`ui/settings/ProfitDisplayPreferences.kt`): не показывать деньги там, где
  пользователь их выключил.
- Показ расхождений отключается тумблером в тех же настройках. Тумблер прячет
  **показ**, но не отключает сверку: расхождение продолжает писаться в `note`,
  иначе через полгода не останется следов — а именно по такому следу и нашлась
  история с 1500.
- `ProfileYearStatsSection` сейчас чистая презентация, `stats` приходят
  готовыми. Правка идёт колбэком наверх, хранилище в секцию не тащим.

## 6. Профиль: цена на сейчас и вперёд

В профиле — цена занятия, диагностики, интенсива и налог. Это правда про
текущий месяц (принцип 1.3), и она же уезжает в новые месяцы по мере их
наступления.

Смена цены в профиле применяется **ко всему текущему месяцу**, включая уже
прошедшие его дни. Прошлые месяцы не задевает.

### 6.1. Происхождение значения: АВТО и РУЧНОЕ

Сегодня отличить «пользователь вписал 1400» от «приложение подставило 1400»
невозможно: единственный признак — `== 0.0`, то есть «не задано»
(`YClientsCalendarSync.kt:239`). Из-за этого автообновление либо не сработает,
либо затрёт ручной ввод.

| Происхождение | Кто выставил | Может ли приложение обновить |
|---|---|---|
| **АВТО** | приложение из данных API | **да**, при каждой закачке |
| **РУЧНОЕ** | человек | **нет**, только сообщить о расхождении |

Тронул поле — значение становится РУЧНЫМ навсегда.

**Цена до первого логина** (человек вписал что-то при создании профиля) —
АВТО. Это заглушка: после синхронизации с YClients цена подтягивается, человек
**видит её в профиле** и при необходимости правит. Подтянутая цена — основная
на текущий месяц; поправленная становится РУЧНОЙ и больше не перезаписывается.
Механика ввода в профиле уже есть, новых экранов не нужно.

Что это даёт: ставка 1500 с августа 2026 появится в API после первого
отработанного дня и **подставится сама** тем, кто цену не трогал. Тем, кто
вписал своё, — останется их значение плюс ненавязчивая строка о расхождении.

### 6.2. Откуда приложение берёт цены

| Поле | Источник | Ловушка |
|---|---|---|
| `pricePerSession` | ставка из детализации последнего начисления | не цена клиента: 1400, а не 3000 |
| `pricePerDiagnostics` | `salary_sum` позиции с диагностикой | **2250**, тогда как цена клиента 4500–4700 — ошибка ровно вдвое |
| `pricePerIntensiveChild` | локально, 1400 ₽ за пришедшего ребёнка | в YClients группы идут отдельным счётчиком `group_services_count` |
| `monthlyTaxAmount` | только руками | YClients про налог не знает |

Цены **по видам работ** берутся из детализации начисления, а не из посуточного
расчёта: там у каждой позиции свой `title` и свой `salary_sum`. Посуточный
даёт только сумму за день. Диагностик за всю историю три штуки — данных мало,
но они точные.

Побочно это заготовка карты «услуга → цена» (8.2): приложение уже знает список
видов работ со ставками, а раскладывает пока в три поля профиля.

### 6.3. Старую автоподстановку чинить, а не выбрасывать

`YClientsCalendarSync.kt:239-246` берёт самое частое значение
`ServiceData.cost` — это оплата деньгами (`0` у трети записей, абонемент),
а не ЗП. Диагностика ловится по словам `"диагностика"`, `"пробн"`, `"тест"`
(строка 233) и получает цену клиента вместо ставки.

Сам механизм по замыслу верен и нужен принципу 1.2 — сломан источник.
Чинится: правильный источник (6.2) плюс признак АВТО/РУЧНОЕ (6.1).

## 7. Первый запуск

Первый успешный логин в YClients — не завершение профиля. `completeRegistration()`
(`ui/profile/ProfileViewModel.kt:106`) про имя и вид деятельности, к YClients
отношения не имеет, токен живёт отдельно в `TokenStorage`.

Что происходит при первом логине:

1. **Тянем историю** — `salary/period/staff/daily/`, год за запрос
   (>1 года и будущее → 422: обрезать период и повторить).
2. **Заполняем записи месяцев** — цена каждого месяца как `factGross ÷ sessions`,
   `origin = AUTO`, прошедшие месяцы сразу `frozen`.
3. **Выставляем цены в профиле** из последнего начисления (6.2), `origin = AUTO`.
4. **Спрашиваем налог** — единственное, чего в API нет.

Расхождения прошлых месяцев здесь **не разбираем**: их видно в статистике,
и правятся они по клику, когда человек захочет (раздел 5). Прошлая статистика
не критична — незачем держать человека в мастере из-за неё.

Если YClients недоступен (403, офлайн) — вход не блокируется: цены вводятся
руками, история догружается при первом удачном синке.

### Когда качаем дальше

| Что | Когда |
|---|---|
| Факт за текущий месяц | при каждом синке |
| АВТО-цены в профиле | при каждом синке, если изменились в API |
| Факт за прошлый месяц | один раз, до заморозки |
| Вся история | при первом логине и по кнопке «перетянуть» |

Не трогать live-опрос и push: работающие подсистемы, к деньгам отношения
не имеют.

### Повторное перетягивание истории

Кнопка нужна: после переустановки или смены телефона иначе не восстановиться.

| Что | При перетягивании |
|---|---|
| `factGross` | перезаписывается свежим значением |
| Цены с `origin = MANUAL`, `tax`, `note` | **не трогаются никогда** |
| `frozen`, `resolved` | сохраняются |

## 8. Что закладываем под других специалистов

Три вещи, которые стоят немного сейчас и очень много потом.

### 8.1. `staffId` в ключе у всех денежных данных

История месяцев, цены, кэш факта — не «мои цифры», а «цифры сотрудника N».
Сегодня это лишнее поле в JSON, завтра — миграция на живых пользователях.

Каждый специалист логинится **под своим токеном** и видит только себя. Чужие
начисления не запрашиваются никогда — вопрос персональных данных из GAPS п.4
снимается сам собой.

### 8.2. Селектор услуги в цене

Цена описывается как `(fix|percent, значение) для [чего]`. Сегодня «чего» —
три корзины (занятие / диагностика / интенсив), завтра — `service_id`. Важно,
что селектор **есть с самого начала**: добавить его позже — переписать все
цены у всех пользователей.

### 8.3. Sidecar-хранилище метаданных записи

Формат строки расширить нельзя. Проверено: `SessionParser.parseStudent`
(`SessionParser.kt:317`) делает `raw.split("|", limit = 5)`, и `comment` —
последнее поле, оно намеренно глотает весь хвост вместе с `|` внутри.
Дописать `service_id` в конец физически невозможно — он уедет в комментарий.
GAPS п.3 не преувеличивает.

Обходной путь, не задевающий ни парсер, ни экспорт архива, ни
`ArchiveSyncCompare`: **отдельное хранилище** `SessionSlotKey → метаданные`.

```
ключ:      SessionSlotKey.build(name, date, startTime, kind)
значение:  record_id, service_id, activity_id, first_cost
```

`SessionSlotKey` (`notifications/SessionSlotKey.kt`) уже существует, стабилен
и используется детектором изменений. Заполняется в `YClientsCalendarSync`,
**пока никем не читается**.

Смысл — начать писать сейчас, чтобы через полгода была история. За прошлое
дособирается из `/records`, пока есть права. Переход на формат V2 — когда
упрёмся, а не сейчас.

### 8.4. Хранение и бэкап

Отдельный `SalaryLedgerStore` (DataStore + JSON, по образцу `CalendarDataStore` —
там есть `corruptionHandler`, повторить обязательно). **Не** внутрь
`UserProfile`: там уже 12 полей в одном JSON, а здесь растущий список.

Ручные правки — самая невосстановимая часть данных: факт перетягивается из API,
введённое руками — нет. Значит история месяцев обязана попадать в бэкап.

Отдельного механизма не нужно: `CalendarDataStore.exportAllData()` (строка 298)
отдаёт `Map<String, String>`, где значение — вложенный JSON, и прецедент
расширения уже есть (`ArchiveNotificationStore.EXPORT_KEY`). Добавляем ключ
`salary_ledger` тем же способом.

Условие: **отсутствие ключа в старом файле означает «не трогать историю»,
а не «очистить»** (в `restoreAllData` обязателен только `saved_day_data`,
строка 325).

## 10. Налог

Сейчас: 6500 ₽ в месяц, фиксированно, каждый месяц, без исключений (в том
числе за февраль–май 2026 — там была ошибка начисления, а не надбавка).

Это не 6 % с оборота: при 190 000 ₽ за май 2026 самозанятость дала бы 11 400 ₽.
Цифра — договорённость, а не расчёт.

**Решено: оставляем как есть** — одно число в профиле, дефолт для всех месяцев,
с возможностью переопределить конкретный месяц в его записи (`tax`).

Открыто на потом: у разных специалистов разное оформление (самозанятость, ИП,
трудовой договор), и налог может быть процентом. Модель «дефолт + правка по
месяцу» это выдержит; отдельная схема расчёта — когда появятся реальные данные.
