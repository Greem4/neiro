## Высоко

### S1. Высоко — logout не отменяет воркер догона событий

**Файлы:** [`auth/LogoutCoordinator.kt:24–36`](../../app/src/main/java/ru/greemlab/neiro/auth/LogoutCoordinator.kt),
[`push/PushEventsSyncCoordinator.kt:13`](../../app/src/main/java/ru/greemlab/neiro/push/PushEventsSyncCoordinator.kt),
[`push/PushRegistrar.kt:63–71`](../../app/src/main/java/ru/greemlab/neiro/push/PushRegistrar.kt),
[`push/PushEventsSyncer.kt:26–67`](../../app/src/main/java/ru/greemlab/neiro/push/PushEventsSyncer.kt)

**Механизм:** `LogoutCoordinator.logout()` гасит `push_keepalive`, воркеры
уведомлений и легаси-имена, но про уникальную работу `push_events_sync` не знает
— в списке отмен её нет. Работа ставится по нуджу `sync_events` из
`NeiroFirebaseMessagingService` и живёт своей жизнью.

Дальше по шагам. `PushRegistrar.onLogout()` (строка 68) сбрасывает курсор:
`PushEventsCursor.reset(appContext)` — комментарий рядом прямо объясняет, зачем:
«иначе после входа под другим аккаунтом догон начнётся с чужого id и пропустит
его события». Но параллельно работающий `PushEventsSyncer.syncNow()` уже прошёл
проверку `isLoggedIn` (строка 30), держит свой `Mutex` и в конце каждой страницы
выполняет `PushEventsCursor.markSeen(appContext, body.lastEventId)` (строка 59).
Этот вызов отрабатывает **после** `reset()` и возвращает курсор чужого аккаунта.

Второй эффект того же гейта: `PushEventCalendarApplier.apply()` (строка 54)
пишет события старого аккаунта в `dayData` уже после того, как `logout()`
завершился.

**Достижимость:** нудж приходит при любом изменении календаря с payload > 3 КБ
(`fcm.py:60`, порог 3072 байта) — то есть при пачке событий, что и бывает в
момент, когда пользователь возится с настройками. Догон также стартует из
`LiveApiCoordinator.onStart` (строка 54) — то есть при каждом открытии
приложения, а «сменить аккаунт» нажимается из открытого приложения. Оба пути
пересекаются с логаутом штатно, гонка не экзотическая.

**Последствие:** после входа другим сотрудником `setIfAbsent` не сработает
(курсор не ноль), и догон запросит события «с чужой позиции» — часть событий
нового аккаунта не придёт, а календарь мог получить чужие правки.

**Фикс:** отменять `PushEventsSyncCoordinator.WORK_NAME` в `LogoutCoordinator`
рядом с `PushKeepAliveCoordinator.cancel`; в `PushEventsSyncer.syncNow` перед
каждым `markSeen`/`ack` перепроверять `isLoggedIn`. Имя работы уже вынесено в
константу — брать её, а не строку.

### K1. Высоко — admin-эндпоинты открываются ключом из APK

**Файлы:** [`server/app/main.py:50–65`](../../server/app/main.py) (строка 54),
[`server/app/config.py:10`](../../server/app/config.py)

**Механизм:**

```python
admin_key = settings.admin_api_key or settings.api_key
```

`admin_api_key` объявлен как `str = ""`, то есть пустая строка — валидное
значение, а не ошибка старта. При пустом `ADMIN_API_KEY` админский ключ
становится равен `API_KEY` — тому самому, что попадает в APK через
`BuildConfig.NEIRO_PUSH_API_KEY` и уходит в `PushClient.authHeader()`.

За `verify_admin_api_key` лежат `/health` (число аккаунтов и устройств),
`/v1/admin/overview` (`company_id`, `staff_id`, метки устройств, версии
приложения, тексты ошибок) и `/v1/admin/test-push` (рассылка на все устройства).

**Достижимость:** ключ извлекается из APK строками, без реверса — это уже
зафиксировано в [`OUT_OF_SCOPE §4.2`](../audit-17.07.26/OUT_OF_SCOPE.md) как
принятый компромисс **для клиентских эндпоинтов**. Расширение того же ключа на
админские — не компромисс, а следствие фолбэка. Открыта дыра прямо сейчас или
латентно, зависит от `.env` на Pi: из репозитория это не видно, `.env.example`
подсказывает задать `ADMIN_API_KEY=replace-me`.

**Фикс:** убрать фолбэк — `admin_api_key: str` без значения по умолчанию
(pydantic-settings уронит старт при отсутствии) либо явная проверка
«не задан → 503». Перед правкой убедиться, что `ADMIN_API_KEY` задан в `.env`,
иначе сервис не поднимется.

### D1. Средне — прогрев `TokenStorage` обгоняется инициализацией на main

**Файлы:** [`NeiroApplication.kt:26, 33–34`](../../app/src/main/java/ru/greemlab/neiro/NeiroApplication.kt),
[`sync/AutoSyncCoordinator.kt:46`](../../app/src/main/java/ru/greemlab/neiro/sync/AutoSyncCoordinator.kt),
[`sync/LiveApiCoordinator.kt:38`](../../app/src/main/java/ru/greemlab/neiro/sync/LiveApiCoordinator.kt),
[`data/network/TokenStorage.kt:20, 120–141`](../../app/src/main/java/ru/greemlab/neiro/data/network/TokenStorage.kt)

**Механизм:** фикс `D7` прошлого аудита прогревает хранилище на IO:

```kotlin
appScope.launch { YClientsClient.getTokenStorage(this@NeiroApplication) }   // :26
...
AutoSyncCoordinator.initialize(this)   // :33 — main
LiveApiCoordinator.initialize(this)    // :34 — main
```

Но обе `initialize` синхронно вызывают `YClientsRepository.getInstance(appContext)`
(`AutoSyncCoordinator.kt:46`, `LiveApiCoordinator.kt:38`), а конструктор
репозитория первым делом дёргает `YClientsClient.getTokenStorage(context)`.
Метод синхронизированный: если корутина прогрева ещё не дошла до создания
`TokenStorage`, main-поток входит в `createSecurePrefs` сам, а если дошла — main
блокируется на `synchronized` до её конца. В обоих случаях main ждёт
`MasterKey.Builder().build()` + `EncryptedSharedPreferences.create()`, то есть
AndroidKeyStore и дисковый I/O.

**Достижимость:** каждый холодный старт. Гонка выиграна прогревом только если
планировщик успел отдать корутине квант между строками 26 и 33 — а это два
вызова подряд без единой точки приостановки.

**Фикс:** либо перенести `AutoSyncCoordinator.initialize`/`LiveApiCoordinator.initialize`
в ту же `appScope.launch`, оставив на main только `ProcessLifecycleOwner.addObserver`
(он main-only, это указано в комментарии), либо сделать создание `TokenStorage`
явно ожидаемым (`Deferred`), чтобы «прогрев» действительно был прогревом.

### D2. Средне — 401 от запоздавшего запроса гасит только что поднятую сессию

**Файлы:** [`data/network/YClientsRepository.kt:71–72, 248–264`](../../app/src/main/java/ru/greemlab/neiro/data/network/YClientsRepository.kt)

**Механизм:** `login()` ждёт хвост предыдущего логаута — `logoutOn401Job?.join()`
(строка 72). Это закрывает случай «401 → logout идёт → пользователь вошёл». Но
`handleUnauthorized()` первым делом безусловно выполняет `tokenStorage.clear()`
(строка 250), ещё до проверки `logoutOn401InProgress`. Если 401 приходит от
запроса, отправленного **до** нового входа, а ответ доехал **после** — токены
свежей сессии стираются, и второй раз logout уже не запускается
(`compareAndSet` вернёт `false`, если предыдущий ещё числится идущим, либо
запустится новый полный logout поверх нового входа).

**Достижимость:** `handleUnauthorized` вызывается из трёх мест —
`fetchRecords` (строка 191), `detectAndSaveStaffId` (295), `getClients` (353).
`fetchRecords` ходит постранично (до 50 страниц по 200 записей) с
`RetryInterceptor` и `callTimeout` 60 с, то есть один вызов легко живёт десятки
секунд. Сценарий: сессия протухла → синк получил 401 на первой странице →
пользователя выкинуло на форму входа → он вошёл за 10 секунд → долетает 401 от
`getClients`, запущенного тем же экраном → сессия обнулена, пользователь снова
на форме.

**Замечание про документацию:** в [`REPORT.md` прошлого аудита](../audit-23.07.26/REPORT.md)
пункт `D1` описан как «зафиксировал поколение сессии при входе». Поколения в
коде нет и не было — проверено `git show 51d8fe3:.../YClientsRepository.kt`.
Реализован был `join()`. Формулировка отчёта не соответствует коду; переписывать
исторический отчёт не стал.

**Фикс:** ввести счётчик поколения сессии (инкремент в `login()` при успехе),
запоминать его в момент отправки запроса и в `handleUnauthorized` чистить
состояние только если поколение не изменилось.

### S2. Средне — keepalive одновременно ретраит и ставит следующее звено

**Файлы:** [`push/PushKeepAliveWorker.kt:36–49`](../../app/src/main/java/ru/greemlab/neiro/push/PushKeepAliveWorker.kt),
[`push/PushKeepAliveCoordinator.kt:43–45`](../../app/src/main/java/ru/greemlab/neiro/push/PushKeepAliveCoordinator.kt)

**Механизм:** при неудаче регистрации воркер возвращает `Result.retry()`
(строка 44) и **одновременно** в `finally` вызывает
`PushKeepAliveCoordinator.scheduleNext()` (строка 47), который ставит работу с
политикой `APPEND_OR_REPLACE`. Отретраенная работа не в терминальном состоянии,
поэтому новый запрос не заменяет её, а дописывается в хвост цепочки. Каждая
попытка ретрая добавляет ещё одно звено — цепочка `push_keepalive` монотонно
растёт и никогда не укорачивается (каждое отработавшее звено ставит следующее).

Это ровно тот дефект, который прошлый аудит чинил под номером `S2` в
`LiveApiRefreshWorker`: «`Result.retry()` и `scheduleNext` не дублируют друг
друга». Файл с фиксом удалён вместе с локальным опросом, а дефект переехал в
keepalive.

**Достижимость:** `registerNow()` возвращает `false` не только при сетевой
ошибке, но и штатно — при `staffId == null`, пустом `userToken`, пустом
`partnerToken`, неудаче получения FCM-токена и при любом 4xx
(`PushRegistrar.kt:126–129, 156–159`). Долгая недоступность сервера или
неверный ключ дают серию ретраев с backoff до 5 часов, каждый — плюс строка в
базе WorkManager.

**Последствие:** не потеря уведомлений (частота звеньев не растёт — они
выполняются последовательно), а разрастание очереди WorkManager и лишние
регистрации после восстановления связи.

**Фикс:** оставить одно из двух. Проще — не возвращать `retry()`, раз `finally`
и так гарантирует следующее звено; интервал следующего звена при неудаче можно
сократить.

### S3. Средне — курсор догона двигается, даже когда событие не применилось

**Файлы:** [`push/PushEventsSyncer.kt:39–63`](../../app/src/main/java/ru/greemlab/neiro/push/PushEventsSyncer.kt),
[`push/PushEventsSyncWorker.kt:16–18`](../../app/src/main/java/ru/greemlab/neiro/push/PushEventsSyncWorker.kt)

**Механизм:** три `runCatching` подряд без проброса `CancellationException`:

```kotlin
val response = runCatching { api.getEvents(...) }.getOrNull()        // :39
runCatching { PushEventCalendarApplier.apply(appContext, mine) }     // :54
PushEventNotifier.notify(...)                                        // :55
PushEventsCursor.markSeen(appContext, body.lastEventId)              // :59
runCatching { api.ackEvents(...) }                                   // :60
```

Два следствия.

1. **Отмена воркера не останавливает цикл.** `PushEventsSyncWorker.doWork`
   (строка 17) тоже оборачивает всё в `runCatching`, не пробрасывая отмену —
   в отличие от соседнего `PushKeepAliveWorker`, где это сделано явно
   (`.onFailure { if (it is CancellationException) throw it }`). При остановке
   работы `CancellationException` съедается, цикл идёт на следующую страницу,
   а `Result.retry()` планирует ещё один прогон уже отменённой работы.
2. **Курсор уходит вперёд при неудаче применения.** Ошибка внутри
   `PushEventCalendarApplier.apply` (запись в DataStore) проглатывается, но
   строки 59–60 всё равно двигают локальный курсор и подтверждают события
   серверу. Изменение календаря потеряно: сервер эти события больше не отдаст,
   а локальный курсор их уже прошёл. Уведомление при этом показано —
   пользователь видит «клиент подтвердился», а в календаре статус прежний.

**Достижимость:** догон вызывается из keepalive (каждые 30–60 мин), из
`LiveApiCoordinator.onStart` и по нуджу — то есть постоянно; отмена воркера
происходит при логауте и при системном отзыве работы.

**Смягчающее:** расхождение календаря лечится ближайшим полным синком при
открытии приложения. Именно поэтому средне, а не высоко.

**Фикс:** пробрасывать `CancellationException` во всех трёх `runCatching`
(как уже сделано в keepalive); двигать курсор и слать ack только если
применение к календарю не упало.

### K2. Средне — SQLite без WAL и схема на каждый запрос

**Файлы:** [`server/app/database.py:34–48`](../../server/app/database.py),
[`server/app/main.py:68–69`](../../server/app/main.py)

**Механизм:** `get_database()` — обычная FastAPI-зависимость, создающая
`Database(settings.database_path)` **на каждый HTTP-запрос**, а конструктор
(строка 38) каждый раз выполняет `_init_schema()` — `executescript` с четырьмя

При этом `connect()` (строки 41–48) не выставляет ни `journal_mode=WAL`, ни
`busy_timeout`: используется дефолтный таймаут `sqlite3.connect` (5 с) и режим
rollback journal, где писатель блокирует читателей.

Поллер (`poller.py`) в том же процессе пишет `update_account_poll_state` каждые
15 с, а при рассылке — ещё и `delete_device` на каждый мёртвый токен.

Сравнение: в сервисе событий это уже сделано правильно —
[`neiro-push-events/app/database.py:183, 190–194`](../../neiro-push-events/app/database.py)
ставит `busy_timeout=5000`, `journal_mode=WAL`, `synchronous=NORMAL`, а
`Database` живёт один на процесс (`main.py:63, 92–93`).

**Достижимость:** любая регистрация устройства, совпавшая по времени с записью
поллера, упирается в `database is locked` через 5 с ожидания → 500 в ответ
приложению → `registerWithToken` вернёт `false` (5xx ретраится трижды) →
[S2](#s2-средне--keepalive-одновременно-ретраит-и-ставит-следующее-звено).

**Фикс:** повторить решение из сервиса событий — один `Database` в `lifespan`,
`app.state.db`, PRAGMA при подключении, `_init_schema()` один раз при старте.

### K3. Средне — детектор изменений сравнивает фингерпринты разных выборок

**Файлы:** [`server/app/poller.py:84–122`](../../server/app/poller.py),
[`server/app/yclients.py:89–104`](../../server/app/yclients.py)

**Механизм:** `changed` вычисляется как «хеш текущей выборки не равен
сохранённому» (строки 91–95). Но выборка не одна и та же от цикла к циклу:
после первого прохода в `changed_after` записывается курсор, и следующий запрос
уходит с `changed_after` + `with_deleted=1`, то есть возвращает **только
изменившиеся записи**, а не весь горизонт.

Последовательность после регистрации устройства:

1. цикл 1: `changed_after is None` → полная выборка → `records_fingerprint = F_полный`,
   `is_first_baseline` → выход без push;
2. цикл 2: `changed_after` задан → в ответе одна-две записи, попавшие в окно
   перекрытия 5 с → `F_2 ≠ F_полный` → **push «календарь изменился», хотя ничего
   не менялось**;
3. цикл 3: та же выборка → `F_2 == F_2` → тишина.

Тот же лишний push повторяется после каждого настоящего изменения: сначала цикл
с изменившейся записью, потом цикл, где окно уже пустое → `F_пустой ≠ F_прошлый`
→ второй push подряд.

**Достижимость:** каждое изменение календаря и каждая новая регистрация.

**Фикс:** не сравнивать фингерпринты инкрементальных выборок — считать
изменением сам факт непустого ответа при заданном `changed_after` (как это
делает сервис событий, где дифф считается по состояниям записей, а не по хешу
пачки).

### K7. Низко — `PRAGMA foreign_keys` не включается ни в одном сервисе

**Файлы:** [`server/app/database.py:41–48, 80`](../../server/app/database.py),
[`neiro-push-events/app/database.py:179–194, 111, 125, 140`](../../neiro-push-events/app/database.py)

В обеих схемах объявлены `FOREIGN KEY … ON DELETE CASCADE`, но SQLite проверяет
внешние ключи только при `PRAGMA foreign_keys=ON`, и это соединение его не
включает (в сервисе событий выставлены `busy_timeout`, `journal_mode`,
`synchronous` — но не `foreign_keys`). Каскады декоративны.

**Достижимость:** сейчас нулевая — кода удаления аккаунта нет ни там, ни там,
удаляются только устройства (у которых зависимостей нет). Дефект проявится при
первой же операции «убрать аккаунт»: осиротеют `record_states`, `events`,
`push_deliveries` и `devices`.

**Фикс:** добавить `conn.execute("PRAGMA foreign_keys=ON")` в `connect()` обоих
сервисов.

### E4. Низко — окно «за сутки» шире суток

**Файлы:** [`neiro-push-events/app/database.py:9–18, 553–564, 566–582`](../../neiro-push-events/app/database.py)

`utc_now_iso()` пишет `2026-07-30T12:00:00+00:00`, а SQLite `datetime('now')`
возвращает `2026-07-30 12:00:00`. Docstring самой функции предупреждает: строки
сравнимы только на уровне даты, «на точности до часа они разъедутся. Ретеншену
этого хватает, **более тонким сравнениям — нет**».

Ровно такие сравнения и используются:

```python
"SELECT COUNT(*) AS c FROM events WHERE created_at >= datetime('now', '-1 day')"   # :558
"... FROM poll_runs WHERE error IS NOT NULL AND started_at >= datetime('now', '-1 day')"  # :573
```

На одинаковой дате символ `T` (0x54) больше пробела (0x20), поэтому любая запись
за нужную календарную дату проходит фильтр независимо от времени. Фактическое
окно — от начала предыдущих календарных суток, то есть до 24 часов шире
заявленного.

**Достижимость:** `events_today` в `/health` и в шапке дашборда, `errors_today`
там же — постоянно.

**Фикс:** сравнивать с `datetime.now(timezone.utc) - timedelta(days=1)` в том же
ISO-формате, что и запись, а не с `datetime('now')`.
