# `neiro-push`: сервис с токенами на сервере

Новый сервис-преемник и новая схема доступа к YClients. Приложение перестаёт
хранить `partner_token`, `user_token` и `company_id`; всё это живёт на Pi, а
телефон получает узкий отзываемый `device_token` и ходит в YClients через
прокси.

Статус: **спроектировано, не реализовано.** Ни строки кода — ниже описано, что
будет написано и почему именно так. Работа идёт по [TASKS.md](TASKS.md),
запуск — по [ROLLOUT.md](ROLLOUT.md), делается в свободное время, без спешки.

## Откуда взялось

Публикация APK в GitHub Releases ([docs/updater/](../updater/README.md))
делает файл доступным кому угодно, а `partner_token` YClients лежит в нём
открытым текстом — обфускация тут не помогает. Первым решением было не класть
токен в сборку и вводить руками. Хозяин проекта развернул задачу правильнее:

> сервер и так работает, будем через него кидать токены и не хранить их на
> устройстве; без регистрации в этих токенах смысла нет — локально люди и так
> всё могут, а при регистрации всё равно надо ждать пуши с сервака.

Это точное описание существующего расклада. Приложение уже офлайн-первое:
календарь, архив, деньги считаются локально. Сеть нужна ровно в одном
сценарии — когда пользователь подключил YClients, а в этом сценарии Pi всё
равно обязателен: уведомления о переносах и отменах приходят пушем оттуда.
Значит второй канал к YClients прямо с телефона ничего не добавляет к
доступности, зато требует держать ключи в APK.

Раз схема доступа меняется целиком, сервис делается заново и получает обратно
короткое имя **`neiro-push`** — третье поколение под старым названием
([DEPLOY.md § Три поколения](DEPLOY.md#три-поколения-сервиса)). Работающий
`neiro-push-events` при этом никто не трогает: новый встаёт рядом и гасит его
только после того, как докажет свою работоспособность.

## Что меняется

**Было:**

```
Телефон ──partner_token + user_token──► api.yclients.com
   │  (оба ключа лежат в APK и в EncryptedSharedPreferences)
   └─────partner_token + user_token────► Pi ──► api.yclients.com ──► FCM
        (копия тех же ключей уходит на сервер при регистрации устройства)
```

**Стало:**

```
Телефон ──логин + пароль (один раз)──► Pi ──► api.yclients.com
   ◄──────── device_token ────────────┘
Телефон ──device_token──► Pi ──partner_token + user_token──► api.yclients.com
                           │  (единственное место, где живут ключи)
                           └──► FCM ──► Телефон
```

В APK не остаётся ни одного ключа YClients. Остаётся один секрет — ключ
приложения к своему серверу, и он даёт ровно одно право: попытаться войти,
зная логин и пароль от YClients.

## Что это даёт

| | Было | Стало |
|---|---|---|
| `partner_token` в APK | Есть, извлекается за минуту | Нет |
| `company_id` в APK | Есть | Нет, сервер знает сам |
| `user_token` на телефоне | Хранится бессрочно | Нет, только на сервере |
| Утёк секрет с телефона | Полный доступ к API филиала | `device_token` одного устройства, отзывается кнопкой |
| Сменить `partner_token` | Пересобрать и раскатать APK | Правка `.env` на Pi, перезапуск |
| Отобрать доступ у телефона | Никак | Отзыв устройства в дашборде |
| Определение `staff_id` | Клиент угадывает по имени | Сервер, один раз при входе |
| Публичный путь | `/v2`, а внутри ещё раз `/v1` | Просто `/v1` |

## Чем платим

Честно, одним пунктом: **подключённый режим перестаёт работать, если Pi
недоступен**. Раньше умерший Pi означал «нет уведомлений», теперь — ещё и «нет
синхронизации». Локальные данные при этом читаются и правятся как обычно, но
свежих записей из YClients не будет.

Разбор — [RISKS.md § Единая точка отказа](RISKS.md#единая-точка-отказа). Там
же о том, почему запасной прямой канал не решение: он требует ровно тех
ключей, ради устранения которых всё и затевается.

## Принятые решения

| Решение | Как и почему |
|---|---|
| Новый сервис рядом, а не переделка работающего | Старое приложение продолжает жить на `neiro-push-events` до последнего дня; откат — установка прошлого APK |
| Имя `neiro-push`, путь `/v1` | Возврат к короткому имени; nginx больше не срезает префикс, поэтому `/v1/auth/login` и снаружи, и внутри |
| Прокси, а не выдача токенов клиенту | Отдать `user_token` телефону — вернуться к тому, с чего начали |
| Ответы YClients пробрасываются как есть | Модели и парсеры в приложении не переписываются: экономия и меньше риска |
| Поллер, события, дашборд переносятся из `neiro-push-events` | «С чистого листа» — про схему доступа, а не про обкатанный код границ YClients |
| `partner_token` — из `.env` сервера | Он один на все аккаунты; в БД он оказался только потому, что приезжал с телефона |
| `device_token` хранится хэшем | Утечка дампа БД не даёт готовых токенов |
| Пароль YClients не хранится нигде | Используется один раз при входе и забывается; протух `user_token` — просим войти снова |
| Ротация `partner_token` — последним шагом | Пока живы старые сборки, старый токен ещё нужен ([ROLLOUT.md](ROLLOUT.md#шаг-6--уборка)) |
