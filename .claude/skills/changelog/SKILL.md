# Заметки к релизу вместо автора

Раздел `## [Не выпущено]` в [`CHANGELOG.md`](../../../CHANGELOG.md) заполняет
агент, а не человек. Человек пишет код и сливает PR; ходить и вспоминать
«что там было заметного» он не должен — за это отвечает этот навык.

Заметки уезжают в релиз как есть: `release.yml` вынимает раздел версии из
`CHANGELOG.md` и кладёт его в описание релиза на GitHub. Что здесь написано —
то и прочитает человек, обновляющий приложение.

## Что делать

1. **Взять изменения.** По умолчанию — с последнего тега:

   ```bash
   git describe --tags --abbrev=0          # прошлый тег, например v0.1.5
   git log --oneline <тег>..HEAD
   git diff --stat <тег>..HEAD
   ```

   В ветке под PR — `git diff main...HEAD`. Просят описать конкретный PR —
   `gh pr diff <номер>`.

2. **Понять, что из этого видно пользователю.** Смотреть не на коммиты, а на
   диффы: одно исправление часто размазано по трём коммитам, а три коммита
   «мини фикс» бывают одним изменением на экране.

3. **Записать в `## [Не выпущено]`**, заменив собой заглушку «Пока пусто…».
   Заголовки внутри — только эти четыре, и только те, под которые есть
   что написать: `### Добавлено`, `### Изменено`, `### Исправлено`,
   `### Убрано`.

4. **Показать написанное пользователю** и сказать, чего в заметки не попало и
   почему (рефакторинг, тесты, документация) — чтобы он мог возразить.

## Как писать

Пишем для педагога с телефоном, а не для того, кто читает код. Проверка одна:
**поймёт ли это человек, который никогда не открывал репозиторий.**

Формат записи — жирная суть одной фразой, дальше объяснение:

```markdown
- **Кнопки «Обновить» и «Пропустить» не выезжают за края** — при крупном
  системном шрифте подпись вылезала за границу кнопки. Теперь, если рядом обе
  не помещаются, они встают друг под другом во всю ширину.
```

Правила, взятые из уже написанных разделов 0.1.0–0.1.5:

- **Название экрана и кнопки — как в приложении.** «Экран „О программе“»,
  а не `AboutScreen`; «Профиль», а не `ProfileViewModel`.
- **Что человек увидит и сделает**, а не какой класс поменялся. Имён классов,
  файлов, пакетов и номеров issue в заметках нет вовсе.
- **Если изменение требует действия** — сказать об этом прямо. Так было в
  0.1.3: «Обновиться на эту версию придётся один раз вручную».
- **Строк 2–4 на запись.** Одна строка — сухо, шесть — никто не прочтёт.
- **Ничего заметного не случилось** — так и написать одним абзацем без
  заголовков, как в 0.1.2 и 0.1.4: «Тестовый выпуск — проверка того-то.
  Видимых изменений в приложении нет».

## Чего в заметки не попадает

Рефакторинг, переименования, тесты, правки документации, изменения CI и
внутренние перестановки — всё, что человек с телефоном не заметит. Если после
отсева не осталось ничего, это не повод сочинять: пустой раздел честнее
выдуманного, а `release.yml` в таком случае соберёт описание из git-лога сам.

## Что дальше делает автоматика

`scripts/bump-version.py` (его запускает workflow «Релиз по слиянию PR»)
перенесёт раздел `## [Не выпущено]` под номер новой версии с датой и вернёт
заглушку на место. Руками этого делать не нужно — достаточно, чтобы к моменту
слияния PR в разделе лежал готовый текст.
